# 技术文档

> 版本对照：《技术方案与 MVP 设计》V1.0.45。所有版本号取自本机 `importlib.metadata` / `pip show` 与
> `reports/m5/M5_版本锁定清单.md` 的**实测指纹**，不是文档里抄来的期望值。

## 1. 技术形态一句话

FastAPI 单体服务 + LangGraph 类型化状态机编排的**内网 RAG 知识服务**：Milvus 做混合检索（服务端 BM25 + 稠密 + RRF + 重排），
PostgreSQL 做唯一权威源与审计，Redis 做非权威检索缓存，本地 Ollama qwen2.5:7b 做生成，
React 19 前端经 Nginx 同源反代，Prometheus + Grafana 做可观测，整套用 Docker Compose 单机起。

## 4. 关键实现机制

### 4.1 检索（`src/kee/retrieval/`）

- **中文 BM25 在 Milvus 服务端做**：集合建 `jieba` 分析器的稀疏向量字段，用 `TEXT_MATCH`/稀疏 ANN 出词法命中，
  不在宿主重算 IDF。实测证据：jieba 分析器 Recall@5 **0.7612** vs 默认分析器 **0.399**。
- **混合融合**：稠密腿 + 稀疏腿 → **RRF**（`rrf_k` 可配）→ **BGE-reranker-v2-m3** 重排 Top-N 候选（默认 20 候选）。
- **检索缓存**：`SearchCache`（Redis，`ex=ttl_sec`，非权威、可驱逐），命中即短路整条链路。
  **权限表达式进缓存键**：`make_key(query, mode, expr, top_k)` → `"kee:search:" + sha1(json)`
  （[src/kee/retrieval/cache.py:25](file:///d:/project/know-effect-engine/src/kee/retrieval/cache.py#L25)），
  调用点 [src/kee/retrieval/pipeline.py:188](file:///d:/project/know-effect-engine/src/kee/retrieval/pipeline.py#L188)
  传的是 `build_filter_expr(ctx)` 的**实际产物**，且 `mode` 字段里折进了 `rewrite_mode`
  （`f"{mode}+rw:{rewrite_mode}"`）⇒ 密级上限 / 部门 / 项目任一不同就是不同键，**缓存不会跨身份复用**，
  换改写配置也不会读到另一套配置的结果。三条边界如实说：① 归一化只有 `query.strip()`，不做大小写与空白折叠，
  近重复查询各算一个键（代价是命中率偏低，不是串权）；② 键里**不含 Milvus 集合名**——集合是部署级隔离，
  只有两个集合共用一个 Redis 时才会撞，本部署不是那种形态；③ 缓存命中轮的 `degraded` 与改写来历在检索层被抹掉，
  这条边界已在指标上可见但**未改行为**。上面这几条现在由 3 条测试钉住（`tests/test_retrieval_degraded.py`：
  真实调用点下两个身份 ⇒ 两个键 / 各分量变化 ⇒ 换键 / 归一化只有 `strip()`）。
- **RBAC 强制点在检索层唯一**：`rbac.build_filter_expr` 按部门（行业）/ 项目 / 密级生成 Milvus filter expression，
  空 `industries` 不加子句；身份来自**登录账号**而不是请求头。
- **量纲闸门**：`hybrid` 下稠密腿空结果必须写 `degraded:dense_empty`；`top_score > 1` 直接**拒出读数**——
  防止静默退化成 BM25 后拿几十的分数去过 0~1 量纲的阈值（真出过一次 `36.9408` 的"过闸"读数）。
- **查询改写**：启发式触发 + 准入校验（禁止引入原查询没有的数字）+ 截断打捞，**默认 `off`**
  （单步 P95 843ms 已吃满 800ms 检索门禁）。

### 4.2 编排与答案（`src/kee/qa/`）

- **LangGraph 七节点有限状态机**：`sensitive_gate → rewrite → retrieve → retrieval_gate → generate → enforce → confidence`，
  三处 `conditional_edges` 可提前 END；指标侧出口标签是 **10 值闭合枚举**（`answered` / `sensitive` / `retrieval_gate` / `generation_failed` /
  `unparseable` / `declared_no_evidence` / `no_citation` / `marginal_evidence_refusal` / `empty_conclusion` / `graph_exception`，
  闭合枚举在 `src/kee/obs/metrics.py:GATED_LABELS`）。
- **引用强制**：结论与引用同轮产出；无来源不出结论；**证据勉强过线不得逐字搬运出结论**（`marginal_evidence_no_derivation`）。
- **答案层复核闸**：`AnswerEngine.gate_unreviewed()` 在检索节点**之后**摘除未复核证据（闸在答案层不在检索层，
  因为复核人必须看得见才能复核），摘光走既有 `no_sufficient_evidence` 出口，notes 记 `unreviewed_evidence_dropped:N`。
- **置信度 = 复合规则分**：`0.45×检索 + 0.35×引用一致性 + 0.20×模型自评`，对外自带 `score_basis=rule_composite_not_probability`；
  **温度单一来源** `kee.qa.answer.load_calibration_temperature()`，T=1.0；`fit_temperature` 有拒绝分支（零方差标签 / 结构零值同义反复）。
- **流式**：`POST /api/v1/answers/stream` 走 SSE，**token 级**；实现方式是"从未闭合的 JSON 信封按路径读已成形字段"，
  因此**不需要**拆成两趟生成；被撤回的片段带显式标记，前端不得静默删。
- **多轮**：会话轮次 + 指代消解；`langgraph-checkpoint-postgres` 已声明但 Checkpointer **本轮未接**（已登记处置，不改 lockfile）。
- **行为等价的证明方式**：`scripts/m3_graph_equivalence.py` 按 commit sha 从 git 抽旧实现当 oracle 逐出口差分，
  豁免项显式登记——**不拿"单测过了"当等价证据**。

### 4.3 知识接入（`src/kee/ingest/` + `src/kee/db/`）

- 解析链是**双后端按条件切换**的（`src/kee/ingest/parsers.py:507` `parse_pdf`）：
  默认 `pdf_parse_backend=auto` —— **先走 pypdf / python-docx 文本层**，只有当某页可抽取字符 < `pdf_min_chars_per_page=40`
  （或显式设 `mineru_onnx`）才转**本地 MinerU-ONNX 后端**：`pypdfium2` 按 `ocr_dpi=150` 渲染页面位图 →
  PP-DocLayoutV2 版面 → PP-OCRv6 det/rec → SLANet-plus 表格结构，三处 `ort.InferenceSession(providers=["CPUExecutionProvider"])`
  （`src/kee/ingest/mineru_onnx.py:80/160-161/299`），权重目录 `mineru_model_dir=D:/modelscope/hub/models/MinerU-4_models_onnx`（本机既有 819MB，零下载）。
  后端不可用或没产出版面文本时**回退 pypdf 并写 notes**，不静默降级。公式未接。
- **生产语料没走 OCR**：当前 193 个知识块来自代码内置的行业文档（`src/kee/ingest/corpus_data.py`），
  属于文本层路径；ONNX 后端是在**扫描件 fixture**（`var/m1/fixtures/扫描件_产品安全手册第1页.pdf` 等）与真实厂商 PDF 上跑的——
  `scripts/verify_m1.py` 步 7.5「扫描件 OCR 入库并可检索」与 7.6「表格结构还原（父块 17 行 × 7 列 + 合并表头、子块行级「列名=值」可检索）」**均实测通过**（17/17）。
- 准入：格式白名单 + `checksum` 指纹查重 + 密级/元数据三级取值（表单 > front-matter > 推断，逐级告警）。
- **Parent-Child 分块**：**子块**入向量库做精准命中，**父块**（整章节 / 整张表）入权威源保结构与表格完整性、
  `parent_id` 全程可查；chunk id 与权威源同命名。**答案组装只喂子块**（带 `章节标题｜` 前缀），
  父块正文回捞**未实现**——四档消融实测接上无可测收益、错配反而劣化；换成长章节再测「相对固定分块」：
  **检索层答案句覆盖 +12.88 个百分点**（固定窗把答案句切断）、**「答得更对」测不出差**、
  接父块两种接法均为**负收益**（见 `reports/m1/M1_父块上下文消融.md`、`reports/m1/M1_分块策略对照.md`）。
- **一致性模型**：PostgreSQL 为**唯一权威源**、向量索引可重建；写入走 **Outbox**，由派发作业投影到 Milvus；
  **每日对账** CLI（`scripts/reconcile_job.py`）比对权威源与索引，Gate 0 ④ 发现率 **19/19**。
- 版本：`document_version` 带 `effective/superseded` 与 `reviewed_by/reviewed_at`（**章在版本上**，回滚不擦章）；
  存量由 `DO $mig$` 一次性回填 `migration:pre-review-gate`（幂等、判列存在）。

### 4.4 权限与审计（`src/kee/api/auth.py` + `src/kee/db/pg.py`）

- 口令 **`hashlib.scrypt`**（n/r/p 参数化），会话令牌只存 **SHA-256 摘要**，`user_session.expires_at` 控 TTL；
  退出登录**撤销全部会话**，管理员可对单用户强制下线。
- 请求头身份通道 `KEE_ALLOW_HEADER_IDENTITY` **默认 false**（脚本改带令牌），验收账号口令随机生成落 `var/verify_credentials.json`（不入库）。
- 审计：**追加写 + `BEFORE UPDATE OR DELETE` 禁改删触发器**。⚠ 触发器**不覆盖 TRUNCATE**（PG 的行级/语句级触发器管不到它），
  项目也**没有**用 event trigger / DDL 触发器去补——`TRUNCATE` 是靠**权限面**挡住的：
  `audit_log` 与触发器函数的属主都换成新建的 **NOLOGIN 超级用户 `postgres`**（函数不换属主的话，
  原角色可以 `CREATE OR REPLACE FUNCTION … RETURN NEW` 把触发器空转，等于不换锁只把钥匙孔磨圆），
  应用连的是**非特权角色 `kee_app`**（非超级用户，表上仅 `INSERT, SELECT`，序列另授 `USAGE, SELECT`），
  而 PG 里 TRUNCATE 需要表属主或超级用户身份（**没有 `GRANT TRUNCATE` 这种权限**，所以只 REVOKE 是堵不住的）。
  原角色 `kee` 是容器 `POSTGRES_USER=kee` 走 initdb 造的 bootstrap 超级用户，**PG 禁止摘它的 SUPERUSER**
  （实测 `permission denied to alter role`）⇒ 只能换钥匙：应用改 `kee_app`、`kee` 设 `NOLOGIN`、
  新建 `kee_admin` 留管理入口（降级 `kee` 之后若不留第二个超级用户，系统就没有任何管理通路了）。
  顺序也有讲究：授权必须排在降级之前，否则会失败在「表已换属主、角色已降级」的半完成状态上。
  **现场验证由应用角色自己那条连接试探**（`probe_bypass`，[scripts/harden_audit_store.py:236](file:///d:/project/know-effect-engine/scripts/harden_audit_store.py#L236)，2026-10-19 本机读数）：
  以 `kee_app`（非超级用户）执行 `TRUNCATE TABLE audit_log` 与 `DELETE FROM audit_log` **双双被拒**，
  两条都停在**权限阶段** `InsufficientPrivilege: permission denied for table audit_log`，审计行数 **1790 → 1790** 一字未动——
  拿超级用户的连接自证「堵住了」等于让被审的对象签字说自己没违规。
  ⚠ 由此得到一个更准的分层说法：**今天挡住的不是触发器，是权限面**；`kee_app` 没有 DELETE 权限时那条
  `BEFORE UPDATE OR DELETE` 触发器根本轮不到执行，它的定位是**第二层**（防日后重新 GRANT 或以属主身份操作）。
  `verify_m1` 把闸门钉成断言（`not rolsuper` + `audit_log` 属主 ≠ `current_user` + 试探前后行数相等）。
  当前 posture（`--check` 只报不写，2026-10-19）：属主 `postgres` · 触发器函数属主 `postgres` · `trigger_present=true` ·
  `kee_app` 权限集 `['INSERT','SELECT']` 且非超级用户、可登录 · 旧角色 `kee` 已不能登录 · 管理口令在 `var/pg_admin_credentials.json`（不入库）。
  **残余风险没被藏起来**：触发器不覆盖 TRUNCATE 这一点依旧成立，超级用户仍能整表抹掉且审计零痕迹，
  所以清场动作必须写在**表外凭据**（`var/gate0/audit_reset.json`）。
- 错误契约：`E4xx` 客户端 / `E5xx` 服务端 / `E9xx` 依赖，结构含 `code/message/trace_id/retryable`；
  统一在 `_fail()` 一个咽喉点计数（`kee_api_errors_total`）。

### 4.5 可观测（`src/kee/obs/`）

- **私有 `CollectorRegistry`**（不用全局）：`create_app()` 在一进程里被多次调用，全局注册表会撞重复注册。
- **19 个 `kee_*` 指标族，标签全闭合**：出口标签取 `state["gated"]` 实际值（不从 `notes` 猜字符串）；
  `degraded` 收敛成 **13 个原因类**（`degraded_class()`），否则每个新分数都会变成一条新时间序列。
  ⚠ 计数别数 `# TYPE kee_` 行——`prometheus_client` 会在首次观测后追加 `_created` 伪族，实测会在 23/24/32 之间浮动，**声明族数是 19**。
- **抓取期依赖探针**与 `/healthz` 共用一份 `dep_snapshot()`，保证"看板上的绿"与"healthz 的绿"不各说一套。
- **进程内累计、不落库**（重启归零）；`kee_process_start_timestamp_seconds` 让"累计值"与 `increase(…[窗口])` 可对账。
- 日志：一行一个 JSON，`trace_id` 与响应体 / 审计 / `session_turn` 同源；`configure_logging()` 幂等；
  九个噪声 logger（httpx/httpcore/urllib3/pymilvus/transformers…）压到 WARNING。
- Langfuse：默认关闭，后台线程 + 队列满丢弃并计数，**目标地址必须回环/RFC1918/链路与白名单名**（`in_domain_host`），
  公开 https 地址即使启用也拒绝；载荷为官方 ingestion 批量事件（trace + span + generation），
  span 起止由 `timings_ms` 按执行顺序**回推**（编排节点本身不计时）。

### 4.6 评测与复验（`src/kee/eval/` + `scripts/`）

- 评测集装配 `build_eval.py` 生成 qrels；**dev/test 半区按 qid 哈希取模**（`<4` 为 dev），
  参数网格（OFAT，9 格）**只在 dev 上跑**，门禁只认**预先声明基线配置的全样本值**——不许"在同一份测试集上调参再报它的分数"。
- **尺子指纹** `ruler`：题量 / 可判行数 / gold 块总数 / **题面哈希**。改题干等于换查询串，指纹不一致就如实报
  `comparable=false`、`delta=null`、`regressed=null`（**"不可比"不能长成"没回归"**）。
- 回归判定用 **strict gold** 那把尺（section 已被独立第二人证伪为注水尺子）；阈值数值一字未动。
- **探针护栏** `kee.eval.probe_guard`：四个真机探针跑前先判依赖健康，判废即 `return 3` 且不写 artifact——
  起因是 Ollama `/api/tags` 返回 200 但模型加载不了，一次宕机能同时把两条门禁判成通过。
- **双人标注**：547 行 / 63 题，Kappa 按题聚类重采样算 CI；工单有"已填过拒绝覆盖"护栏与 `--only-qids` 局部重出。
- **一条命令复验**：`scripts/ci_local.sh` 十一阶段（含 GPU 互斥停服、`eval` 回归、`warm` 预热、证据 md5 前后对比、服务复原）。

## 7. 已知技术债与边界（如实列出）

1. **API 未进容器**（ADR-12 定案维持现状）：`torch` 不在 pyproject 是根因；实测 CPU 路径合成检索 **5166.9ms**（fp16 CPU 更慢，26153.7ms）
   对 800ms 门禁 ⇒ 容器化只装 CPU torch 不是"慢一点"而是把门禁变成不可达；要 GPU 就得拉 GB 级 CUDA 镜像。
2. **ECE 不达标**：真人标签下 0.2006 > 0.10，方向为欠置信；温度缩放两档均拒绝采纳。
3. **断网端到端未证**：`internal: true` 断掉宿主↔容器通路，`enable_ip_masquerade=false` 在 Docker Desktop 上实测切不掉容器出网。
4. **公式解析未接入**（MinerU-ONNX 只做版面 + OCR + 表格结构）。
5. **检索侧词法缺口**：口语化查询与书面证据词法不重合（q-044 排名在噪声级别，第 1 名曾只领先第 2 名 0.0002）。
6. **`/metrics` 免鉴权**（敞口未闭）：前提三条同时成立——只绑回环、Nginx 不反代该路径、标签无业务内容。
7. **Langfuse 容器未实跑**：代码侧已用本地采集器**实采**过载荷（作答轮 3 事件 / 敏感轮 1 事件 / 拒答轮 2 事件），真镜像待裁。
8. **业务两条指标不可测**：需要上线前基线与真人时间维度。
