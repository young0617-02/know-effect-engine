## 1. 业务问题 → 技术方案 → 代码定位

### 1.1 业务背景

数字技术服务企业的交付知识有三个特点：**文档多、版本多、权限敏感**。项目结项后，方案、接口规范、运维手册散落在个人网盘与邮件里；新项目反复踩同一个坑；即使找到了文档，也不敢直接拿答案去交付，因为不知道它引的是不是过期版本、有没有经过复核。

系统围绕六个业务痛点设计：

1. 文档写完即沉睡，找不到；
2. 答案不可信，人还得回原文核对；
3. 不知道系统什么时候在「瞎说」；
4. 知识时效与责任人不清，引用了过期版本；
5. 权限敏感，数据不能出内网；
6. 上线与否靠感觉，无法判断改动是变好还是变坏。

## 2. 核心链路与代码定位

### 2.1 知识接入与版本治理

**业务上解决什么**：让一份客户交付文档从「上传」走到「可被安全引用」，并且能回答三个问题——这份文档是谁的、什么版本、有没有人复核过。

**技术实现**

- **准入**：格式白名单、`checksum` 指纹查重、密级/元数据三级取值（表单 > front-matter > 推断，逐级告警）；重复上传必须显式带同一 `doc_id` 才能升版。
- **解析**：`pdf_parse_backend=auto` 先走 pypdf/python-docx 文本层；某页可抽取字符 < 40 时转本地 **MinerU-ONNX** 后端：`pypdfium2` 渲染页面位图 → PP-DocLayoutV2 版面 → PP-OCRv6 det/rec → SLANet-plus 表格结构，三处 ONNX 会话都用 CPUExecutionProvider；后端不可用或没产出版面文本时**回退 pypdf 并写 notes**，不静默降级。
- **分块**：Parent-Child。子块（默认 280 字符，可重叠 40）进向量库做精准命中；父块（整章节/整张表）进权威源保结构与表格完整性，`parent_id` 全程可查。表格行拆成「列名=值」行块，供单元格级问题命中。token 粒度（Child 200/30、Parent 1000/150）**已实现但默认不启用**，生产索引保持 `chars` 口径。
- **一致性**：PostgreSQL 是唯一权威源；写入走 Outbox 异步投影到 Milvus；每日对账 CLI 比对权威源与索引，差异入表并走 Outbox 补偿修复；索引坏了可从权威源 + 向量物料重建。
- **版本治理**：`document_version` 带 `effective/superseded` 与 `reviewed_by/reviewed_at`；复核章落在版本上（回滚不擦章）；reject 会撤下该版本索引；上传者不能自审（职责分离）。

**技术栈**：Python 3.12 · FastAPI · pypdf · python-docx · pypdfium2 · ONNX Runtime（PP-DocLayoutV2 / PP-OCRv6 / SLANet-plus）· PostgreSQL 18 · Milvus 3.0 · Outbox · jieba。

### 2.2 混合检索与权限过滤

**业务上解决什么**：员工用口语化问题，能找到书面语的交付证据；并且检索结果天然只包含他有权看的部门/项目/密级范围，不依赖前端隐藏。

**技术实现**

- **服务端中文 BM25**：Milvus 集合的 `text` 字段启用分析器，`analyzer_params={"tokenizer":"jieba"}`（Milvus 3.0 不接受 `{"type":"jieba"}`）；稀疏字段用 `FunctionType.BM25` 自动生成，`SPARSE_INVERTED_INDEX` + BM25 度量。词法 IDF 在服务端算，不在宿主重算。
- **稠密腿**：BGE-M3 输出 1024 维向量，`FLAT` + `COSINE` 精确检索（语料规模小，避免 ANN 近似损失污染消融结论）。
- **融合与重排**：稠密腿 + 稀疏腿 → **RRF**（`rrf_k=60`）→ BGE-reranker-v2-m3 重排 Top-20 候选。表格行块使用「守住融合名次、只用重排分数」的策略，绕开交叉编码器在 0.97–0.999 饱和区对同表各行只差 1e-3 的排序噪声。
- **权限唯一强制点**：`build_filter_expr(ctx)` 按角色密级上限、行业、项目生成 Milvus filter expression；标识符先过白名单字符校验再拼接；身份来自登录账号而不是可伪造的请求头（`KEE_ALLOW_HEADER_IDENTITY` 默认 false）。
- **缓存与降级**：Redis `SearchCache` 非权威、TTL 可驱逐；**权限表达式与改写模式进入缓存键**，不同身份/不同改写配置不会共用缓存。检索层把稠密腿空结果、超时、量纲异常等收敛成 13 个降级原因类；`top_score > 1` 直接标记 `score_scale_out_of_range`，防止静默退化成 BM25 后拿几十的分数去过 0–1 量纲的阈值。
- **查询改写**：启发式触发 + 准入校验（禁止引入原查询没有的数字）+ 截断打捞；实测单次 P95 **843ms**，已吃满 800ms 检索门禁，因此默认 `off`，只在显式配置时启用。

### 2.3 可信问答编排

**业务上解决什么**：每条结论能点开看到出处；证据不够时明确说「不知道」；敏感内容必须转人工；没复核的知识不能拿来作答。

**技术实现**

- **LangGraph 七节点有限状态机**：`sensitive_gate → rewrite → retrieve → retrieval_gate → generate → enforce → confidence`；三处 `conditional_edges` 可提前 END；出口标签是 **10 值闭合枚举**（`answered / sensitive / retrieval_gate / generation_failed / unparseable / declared_no_evidence / no_citation / marginal_evidence_refusal / empty_conclusion / graph_exception`），指标取 `state["gated"]` 的实际值而不是从 `notes` 字符串猜。
- **引用强制**：结论与引用同轮产出；无来源不出结论；**证据勉强过线不得逐字搬运出结论**（`marginal_evidence_no_derivation`）；空结论不得判成功。
- **答案层复核闸**：`AnswerEngine.gate_unreviewed()` 在检索节点**之后**摘除未复核版本的证据；未复核内容仍可被检索（复核人得看得见），但不进答案证据面。摘光后走既有「无充分依据」出口，并通过 `refusal_reason`（`no_evidence` / `all_evidence_unreviewed`）和 `unreviewed_evidence_count` 把「库里没资料」与「有资料但没复核」分开。
- **敏感闸与转人工**：密级 3 命中时允许答但必须 `needs_human=true`；非作答题用另一把尺判「该不该不答」，避免把正确转人工报成泄漏。
- **置信度**：复合规则分 `0.45×检索 + 0.35×引用一致性 + 0.20×模型自评`；响应自带 `score_basis=rule_composite_not_probability`，温度维持 T=1.0，不称概率。温度缩放有拒绝分支（零方差标签 / 结构零值同义反复）。
- **父块回捞**：`apply_parent_context()` 已按需求实现：按 `parent_id` 从权威源取父块正文、扣掉子块已含段落、按 token 预算整块贴入；父块文字不占证据编号。**两轮实测判净负**，默认关闭，生产索引不按 token 粒度重切（见 4.5）。

**技术栈**：LangGraph 1.2 · Ollama qwen2.5:7b（GGUF Q4_K_M，ctx 4096）· Pydantic v2 · FastAPI · JSON 结构化输出 · 规则评分。

### 2.4 流式与多轮

**业务上解决什么**：长答案逐字出现，用户能提前判断方向是否跑偏；可以就上一轮继续追问，历史会话可恢复。

**技术实现**

- **token 级 SSE**：`POST /api/v1/answers/stream` 用同一份 `initial_state`，一次 JSON 生成即可从未闭合信封按路径读已成形字段逐段推送；事件序列 `retrieval → delta* → answer`。`delta` 一律带 `provisional:true`；最终没成为答案的文字必须标「已撤回」，不能静默删除；被引用强制丢掉的要点记 `provisional_lost`。
- **首字口径**：门禁认 **`first_visible_ms`（首个可读字）**，不是信封首字符 `{`；实测首个可读字 p50 **695.4ms** / p95 **859.2ms** / max 1008.6ms（n=24）。
- **多轮**：会话轮次落 PostgreSQL `session_turn`，历史列表只返回自己的会话，详情带整包答案；多轮指代消解在检索前生效，补全后的查询同时进检索与生成提示词，对外 `question` 仍是用户原话。LangGraph Checkpointer 本轮未接，多轮状态以 PG 为唯一权威源（已知债：无断点续跑）。
- **前端 SSE 客户端**：因为 EventSource 不支持 POST、不能带自定义身份头，前端自写 SSE 分帧器，按规范处理空行帧边界、多行 `data:`、注释心跳与 CRLF；依赖挂掉时在建流前走契约错误，避免界面停在「收到一半」。

**技术栈**：SSE · FastAPI StreamingResponse · 手写增量 JSON 解析器 · React 19 · TypeScript · PostgreSQL `session_turn`。

### 2.5 权限、审计与账号

**业务上解决什么**：账号、角色、会话可管理且可强制下线；「谁问了什么、看了哪段」可追溯且不可篡改；数据不靠前端隐藏来保证隔离。

**技术实现**

## 4. 工程难点与决策（面试展开）

### 4.1 8GB 单卡如何同时跑 BGE-M3、reranker 与 7B

**难点**：内网单机没有第二张卡；嵌入、重排、生成三个模型同时驻留会 OOM，或者 Ollama 把旧模型 LRU 掉，表现为「模型不可达」而不是报错。

**做法**：
- `ResidencyScheduler` 支持 `time_sharded / co_resident / cpu_sharded` 三种策略，按角色 acquire/release，空闲释放；`VramSampler` + `OomWatchdog` 采样显存并在越界时报警。
- 生成走 Ollama HTTP，嵌入/重排走本地 PyTorch CUDA；冷启动与热态分开报，复验脚本必须先 `api_warm.py` 预热，否则验收会把冷启动读成失败。
- 为容器化决策做设备对照实验：同一套权重一次检索，`cuda+fp16 178.1ms / cpu+fp32 5166.9ms / cpu+fp16 26153.7ms`。结论不是「CPU 慢一点」，而是「只装 CPU torch 会把 800ms 检索门禁变成不可达」。

**技术栈**：PyTorch 2.14+cu130 · CUDA 13 · Transformers 5.19 · Ollama · NVML/显存采样 · 时间分片驻留。

**代码**：[registry.py:34](file:///D:/project/know-effect-engine/src/kee/models/registry.py#L34)、[:80](file:///D:/project/know-effect-engine/src/kee/models/registry.py#L80)、[gpu.py:15](file:///D:/project/know-effect-engine/src/kee/models/gpu.py#L15)、[:105](file:///D:/project/know-effect-engine/src/kee/models/gpu.py#L105)、`src/kee/gate0/g01_vram_scheduler.py`、`scripts/m4_cpu_path_probe.py`。

**证据**：Gate 0 ① 零 OOM、嵌入+重排与 7B 可共存；P95 检索 314ms；容器化对照见 `docs/ADR-12_容器化代价实测.md`。

### 4.2 评测尺子：如何避免「在自己的测试集上调参再报分」

**难点**：检索参数网格如果全量跑完再挑最好一格，分数会系统性虚高；gold 口径定义不清会让「章节内所有子块都算 gold」把 Recall 注水；改题干等于改查询串，回归对照会拿两把不同的尺子比。

**做法**：
- 按 `qid` 哈希取模分 dev/test（`<4` 为 dev），参数网格只在 dev 上跑；门禁只认预先声明基线的**全样本**值。
- `ruler` 指纹含题量/可判行数/gold 块总数/题面哈希；指纹不一致就报 `comparable=false`、`delta=null`、`regressed=null`，不给假的 `regressed=false`。
- `build_eval` 每次装配产出 `gold_defects`（命中面 >3 段即缺陷，豁免必须写理由），并检测「题面点规范但 gold 在别类文档」的 `doc_scope_defects`。
- 组织双人盲标 63 题 / 547 行，按题聚类 Bootstrap 95% CI；用 strict vs section 两套 gold 证明 section 注水（κ 0.8066 vs 0.5595，差值 2000/2000 次同号）。

**技术栈**：Python · numpy · Bootstrap 重采样 · Cohen's κ · CRC32 题面哈希 · pytest。

### 4.6 审计防篡改：触发器管不到 TRUNCATE，怎么办

**难点**：PostgreSQL 的行级/语句级触发器**不覆盖 `TRUNCATE`**；如果应用角色是超级用户，表级 REVOKE 也无效，一句 `TRUNCATE TABLE audit_log` 就能把防篡改表抹干净且不留痕。

**做法**：
- `audit_log` 与触发器函数属主改为 NOLOGIN 超级用户 `postgres`；应用改用非特权角色 `kee_app`（表上仅 INSERT/SELECT，序列另授 USAGE/SELECT）；旧 `kee` 设 NOLOGIN，另建 `kee_admin` 保留管理入口。
- 顺序有讲究：授权必须排在降级之前，否则会失败在「表已换属主、角色已降级」的半完成状态。
- 验证必须用**应用角色自己的连接**试探，不能拿超级用户自证。

**技术栈**：PostgreSQL 18 · 触发器 · 角色/属主/权限面 · psycopg 3。

**代码**：[pg.py:181](file:///D:/project/know-effect-engine/src/kee/db/pg.py#L181)、`scripts/harden_audit_store.py`、`scripts/reset_audit_state.py`、`verify_m1.py` 的审计断言。

**证据**：以 `kee_app` 执行 `TRUNCATE` 与 `DELETE` **双双被拒**，审计行数 **1790 → 1790** 一字未动；残余风险（超级用户仍可整表抹除）如实保留在风险登记册。

## 6. 面试问答速查

**Q1：你怎么保证答案可信？**
三层：检索层只给有权看的证据；生成层强制「结论与引用同轮产出，无来源不出结论」；答案层用复核闸摘掉未复核版本，并用 `refusal_reason` 区分「没资料」与「有资料没复核」。读数：引用落 gold 98.39%、零引用结论 0、无依据拒答 7/7、敏感转人工 5/5。代码在 `src/kee/qa/graph.py:301`、`src/kee/qa/answer.py:284`、`src/kee/qa/answer.py:319`。

**Q2：检索指标怎么证明不是调参调出来的？**
dev/test 按 qid 哈希半区隔离，参数网格只在 dev 上跑；门禁只认预先声明基线的全样本值；`ruler` 指纹含题量/可判行数/gold 总数/题面哈希，尺子变了就报「不可比」，不给假的 `regressed=false`。同尺子复跑 `delta_strict=0.0`。代码在 `scripts/m2_eval.py:242` 和 `:289`。

**Q3：为什么不用 ragas 官方包 / Langfuse SDK / 把 API 容器化？**
ragas 会拖 `scikit-network → numba`，顶掉硬钉的 `numpy==2.5.3`，且默认走 OpenAI 客户端；Langfuse SDK 会拖整套 OpenTelemetry，为一个默认关闭的功能不值，所以走官方 ingestion 批量接口；API 容器化要拉 GB 级 CUDA 镜像或把检索门禁变成不可达（CPU 路径 5166.9ms vs 门禁 800ms），所以按 ADR-12 保持宿主 API。三条都是实测后的取舍，不是「没做」。

**Q4：8GB 显存怎么跑三个模型？**
嵌入/重排走宿主 CUDA，生成走 Ollama；`ResidencyScheduler` 做时间分片与空闲释放，`VramSampler/OomWatchdog` 采样显存；冷启动与热态分开报，复验先预热。Gate 0 实测零 OOM，嵌入+重排与 7B 可共存。代码在 `src/kee/models/registry.py:34`、`src/kee/models/gpu.py:15`。

**Q5：这个项目最大的失败或取舍是什么？**
两件事：① 父块回捞按需求实现后两轮实测判净负（可完成率 -2.0 题当量、引用落 gold -4.0 题当量），所以默认关、生产索引不重切；② ECE 0.2006 > 0.10，校准不达标，所以复合分只称「规则分」不称概率，温度缩放不采纳。两件都保留证据，不把 fail 写成 pass。

**Q6：多轮和流式真的有用吗？**
流式有硬读数：首个可读字 p95 859.2ms，达 <1.2s 门禁；撤回不静默删除。多轮机制成立（14/14 发生消解，检索层救回 1 道 / 丢掉 0 道），但答案层净收益为 0，所以不能写「多轮提升效果」——只能说「多轮可用，收益未被证明」。
