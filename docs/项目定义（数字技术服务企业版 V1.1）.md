# 企业级知识库 RAG Agent · 项目定义（数字技术服务企业版 V1.1）

> **基准行业**：数字技术服务 / IT 服务与数字化运营（面向多行业的咨询、解决方案与交付服务）。
> **文档用途**：以基准行业的属性为坐标，定义本项目的定位、用户、场景与验收口径。
> **口径声明**：本项目处于**系统设计与方案定型阶段**，文内所有量化数字均为 **设计目标 / 验收门禁**，**非实测达成值、非已上线数据**。
> **执行主体**：个人独立设计与开发。

## 四、核心场景

**主流程（在线问答闭环）**：员工在内部知识门户 / IM 插件中以自然语言提问 → Agent 检索多源知识库 → 输出**带引用来源的结构化答案** → 可**对话式追问**。

- **输入**：自然语言问题（+ 提问者角色 / 部门 / 项目 / 权限上下文）
- **输出**：结构化答案 = 结论 + 引用出处（文档 / 章节 / 页码 / 片段）+ 分数（V1.6 起标注为规则分，非概率）+ 免责提示；低置信度显式降级为"初步判断"，敏感问题转人工复核

**支撑流程（离线知识构建）**：项目结项 / 文档上传 → 准入审核（格式校验 / 重复检测 / 来源可信度分级）→ MinerU 解析 → Parent-Child 分块 → 元数据与版本标注（行业 / 客户 / 项目 / 密级）→ 多存储写入（向量库 / 元数据库 / 可选关系图谱）→ Outbox 对账。

**治理流程**：登录（RBAC）→ 问答 / 文档查询 → 答案复核（通过 / 驳回）→ 知识版本升版 → 全操作审计。

## 五、痛点（现状 vs. 不足）

**现在怎么做**：知识散落在 OA / Wiki / 项目文档库 / 邮件 / IM / 网盘，员工手动翻找或用关键词在多个系统里分别搜；跨行业经验依赖"找熟人问"。

| 痛点 | 为什么不够好 |
|---|---|
| 行业知识资产分散、随项目沉睡 | 数十年沉淀散落无数项目文档，检索靠关键词，命中率低、复用难 |
| 跨行业 / 跨项目经验难复用 | 金融、能源、化工各成体系，方案与组件重复造轮子 |
| 前出客户现场取数慢 | FDE 依赖呼叫总部专家，响应以小时计 |
| 新人上手周期长 | 方法论与行业知识未结构化沉淀，重复问老员工 |
| 内网与企业客户数据敏感 | 内部资料涉密 / 涉合规，不能出域，纯云端方案直接被否 |
| 答案无出处 | 检索结果无法追溯到原文，员工"不敢信、不敢用" |

## 六、成功指标（设计 / 验收目标口径）

**业务指标**
- **交付知识复用率**提升（以"复用命中历史资产的项目占比"度量，设计目标）
- **自助解答率 ≥ 60%**（无需转人工）；重复性提问占比下降 **≥ 30%**
- **FDE / 现场问题响应**：从**小时级 → 分钟级**（P95 完整答案 < 6s；原 < 3s 口径经 Gate 0 实测修订，见十四节）
- **新人上手周期**缩短（以"首次独立完成交付任务"度量，设计目标 ≥ 30%）

**技术指标**

| 指标 | 验收目标 | 测量方式 |
|:---|:---|:---|
| Recall@5 | **V1.3 口径**：主判定 `Hit@5 ≥ 95%` + `strict gold Recall@5 ≥ 85%`；`section gold Recall@5` 作报告值随附。任何 Recall 类数字必须同时给出样本量 n 与 95% 置信区间 | 自建行业 QA 评测集 |
| MRR | ≥ 0.75 | 同上 |
| 引用正确率 | ≥ 90% | 人工抽检 |
| Faithfulness | 报告值（目标 ≥ 90%） | RAGAS / LLM-as-Judge |
| Answer Relevance | 报告值 | RAGAS |
| 幻觉率 | ≤ 10% | 人工 3 级评分 |
| 置信度校准（ECE） | ≤ 0.10 | 校准集 |
| 结构化输出首次成功率 | ≥ 90% | 用例集 |

**成本 / 延迟指标**

| 指标 | 验收目标 | 测量方式 |
|:---|:---|:---|
| P95 检索延迟 | < 800ms | 探针 ｜ **#56 净环境 4 轮合并 p95 334ms（n=100 轮次，含拒答）** |
| P95 完整答案延迟 | **< 3s 还是 < 6s 待用户裁**（两个值同时存在于 DoD#5 与本节，见 V1.19 二.1）。**#56 净环境复测**（生产入口、一问一 session、冷启动单列、清检索缓存，4 轮 / 76 个进生成的轮次）：p50 **3287ms**、p95 **4118.8ms**、max 4548.5ms ⇒ **<6s 过、<3s 不过（68.4% 轮次超 3s）**；轮间 p50 极差 93.6ms 是噪声地板。**流式首 token < 1.2s 已补测并达标**：三种读法同轮量齐（n=24），最严的「首个可读字」p50 695.4 / p95 859.2 / **max 1008.6ms**。历史读数保留：原口径 < 3s 经 Gate 0 ① 实测，256 token 档合并 P95 5990ms（n=12，临界）；96 token 短答案档 P95 2477ms，即原口径在短答案档仍可达 | 探针 ｜ `var/gate0/m5_latency_replicates.json`（`scripts/m5_latency_clean.py` + `m5_latency_merge.py` 可复跑） |
| 置信度校准（ECE） | **报告值**（原为验收目标 ≤ 0.10）；门禁改由「无来源必不输出结论 + 无依据必拒答 + 敏感/低置信必转人工 + 结构化首次成功率 ≥ 90%」四项机制承担（Gate 0 ⑤ 实测：机制全达标）。**ECE 已用真人标签算出**：`answer_prod` n=62 **0.2006**（accuracy 0.9677 / mean_conf 0.7671）、全行为口径 n=67 **0.1857** ⇒ **仍 > 0.10，不达标**；温度缩放两档都不采纳（负类 2 例不可辨识 / 拒答行复合分被规则钉在 0.0，拟合的是同义反复）。标签只配它判过的那一代探针产物（`--probe`，见 V1.19 五） | 校准集 / 机制断言 ｜ `var/gate0/answer_correct_calibration.json` |
| 云端成本 | 预算熔断，无固定云开销 | 预算计数 + 限流 |
| 缓存命中率 | 报告值 | 指标监控 |

## 十、技术方案概览

- **RAG 检索**：Milvus v3.0.0 / BGE-M3（稠密向量）/ 服务端 BM25（`FunctionType.BM25` + jieba 中文分析器）/ RRF 融合 / BGE-reranker-v2-m3 重排 / Parent-Child 分块
- **Agent 编排**：LangGraph StateGraph（确定性工作流，V1.5 起 7 个显式出口、敏感闸前置）/ 查询改写 / 多轮追问（**上文权威源 = PostgreSQL `session_turn`**）/ 引用强制 / 工具白名单
  - V1.5 裁决：Checkpointer 不在本轮交付范围。本文件的「数据存储归属原则」已把 PostgreSQL 定为唯一权威源、
    Redis 为非权威可重建；再引入一套 checkpointer 状态存储等于同一份会话状态存两处。Checkpointer 的独有价值是
    **中断-恢复**，其中断点（人工复核闭环）属后续里程碑，届时应指向同一张 PG 而不是另一套表。
    **代价：链路中途失败只能整条重来，无断点续跑。**
- **大模型工程**：Ollama（**本地单模型 `qwen2.5:7b`** 承担查询改写、工具调用与答案生成；V1.2 起移除 `deepseek-r1:7b` 双模型分工——8GB 单卡不可共存，实测切换冷启 4.6–9.0s/次）/ LiteLLM 网关 / 云端兜底路由 / 复合分数校准（**V1.6 裁决：本轮不启用温度缩放，T=1.0**——Gate 0 那次拟合的标签 在可判集上恒为 1，零方差上拟合只会把分数压向基率；出现有方差的 `answer_correct` 标签后再谈） / Prompt 与 JSON Schema 约束
- **服务与存储**：FastAPI / PostgreSQL 18 / Redis 8 / MinerU / Socket.IO / Docker Compose / Nginx
- **评估与可观测**：RAGAS / 自建评测集 / Langfuse / Prometheus + Grafana

**数据存储归属原则**：向量索引（Milvus）、元数据与版本（PostgreSQL，唯一权威源）、关系图谱（可选，用于实体 / 流程 / 方案关联增强）、运行态缓存与会话（Redis，非权威、可重建）。

## 十一、关键能力设计

### A. 知识库构建与文档解析
- **MinerU 解析 + Parent-Child 分块**：子块用于精准检索，父块补全上下文，兼顾检索精度与上下文完整性。
- **多存储写入架构**：向量库存向量、PostgreSQL 存元数据与版本、可选图谱存关系；定义"**元数据库为唯一权威源、向量索引可重建**"。
- **文档元数据与版本管理**（行业 / 客户 / 项目 / 来源 / 章节 / 密级 / 状态）：支撑**跨行业隔离、跨项目复用、版本回滚**。
- **文档准入流程**（格式校验、重复检测、来源可信度分级）。
- **多格式解析适配**（PDF / Word / 表格）与结构化抽取。

### B. 混合检索与检索质量优化
- **Dense(BGE-M3) + Sparse(服务端 BM25) 双路混合检索**，以 **RRF（k=60）** 融合后交 **BGE-reranker-v2-m3** 重排至 Top-5，解决单一稠密检索对**术语、编号、方案名**类问题召回不全的痛点。
- **Milvus 服务端 BM25 Function** + **jieba 中文 analyzer**，解决默认分析器对中文近乎无效的关键缺陷。**V1.2 配置形态修正**：Milvus v3.0.0 写法为 `analyzer_params={"tokenizer":"jieba"}`（`{"type":"jieba"}` 被服务端拒绝）；实测默认分析器中文 Recall@5 0.399 对 jieba 0.761。
- **查询改写**：将口语化 / 多轮指代问题改写为检索友好的 query。
- **检索参数基线与消融对比**（Dense / Sparse / 混合三组对照），使"效果提升"可归因、可复现。
- **检索结果缓存**（Redis，按 hash 缓存、TTL 可驱逐）。

### C. Agent 编排与问答体验
- 基于 **LangGraph StateGraph** 构建**类型化（Pydantic）问答工作流**（查询改写 → 混合检索 → 重排 → 生成 → 引用校验），以 **Checkpointer** 支撑多轮状态持久化与中断-恢复。
- **证据引用强制**：每条结论必须携带来源，**无来源不出结论**；检索失败走 fallback（澄清追问或明确"未找到依据"）。
- **多轮追问与上下文管理**（指代消解、历史摘要压缩）。
- **本地单模型 + LiteLLM 网关**：`qwen2.5:7b` 单模型承担结构化任务与答案生成（**V1.2 修订**：原「双模型分工」在 8GB 单卡不可行——两 7B 无法共存、切换冷启 4.6–9.0s/次，且同底座能力重叠）；低置信度升级云端兜底。
- **流式对话交互**（Socket.IO 实时流式输出、引用高亮、追问建议）。

### D. 可靠性与一致性
- **Outbox + 每日对账**：写入元数据库后异步写向量库，失败入补偿队列，每日比对差异，解决多存储"静默缺数据"。
- **统一错误码 / 超时 / 重试 / 幂等契约**。
- **降级策略**：检索超时降级纯关键词；生成失败降级"仅返回检索片段 + 标注"。
- **备份与恢复** 与 Docker Compose 编排（healthcheck / 资源限制 / 命名卷）。

### E. 安全与合规
- **四道防线**：数据接入层本地闭环、Agent 层工具白名单 + 输入净化、答案层引用强制 + 降级显式化、知识层准入审核 + 来源分级。
- **RBAC 权限体系**：按**部门 / 项目 / 客户 / 密级**过滤可见知识，在**检索层做权限过滤**，确保"搜得到"的前提是"有权限看"。
- **审计与可追溯**：查询、追问、引用、知识变更全量追加记录，审计表禁改。
- **敏感内容拦截与拒答边界**。

### F. 评测、可观测与交付
- **自建评测集与量化门禁**（Recall@5、MRR、Faithfulness、Answer Relevance、引用正确率、P95 延迟）。
- **离线评估流水线**（RAGAS + LLM-as-Judge + 规则评分 + 版本回归）。
- **可观测体系**（Langfuse 链路 + Prometheus / Grafana + 结构化日志）。
- **一键启动 Demo**（Docker Compose + 架构图 + 使用说明）。
- **成本治理**（云端预算熔断、缓存与 prompt 压缩、本地优先路由）。

## 十三、设计取舍与复盘要点

- **取舍**：为保障在线体验，牺牲部分召回换取低延迟；召回不足时宁可走 fallback 澄清，也不给出无依据答案。
- **典型迭代**：中文分词器若失效（BM25 收益≈0）→ 强制 jieba + 分词人工抽检；长文档召回不全 → 章节级切分 + 查询扩展；多存储不一致 → Outbox + 每日对账。
- **规模化的下一步**：知识量扩大时索引分层 / 分片扩展，评测集同步扩容，并接入在线反馈形成持续评估闭环。
- **为什么自研而非现成平台**：通用平台适合快速验证业务流程，自研更适合展示**底层检索可控性、可评估性与工程化能力**。

### V1.13（2026-10-12，复核闸裁决：把「准入审核」拆成两件事，闸装在答案层）

**这一版改的是需求原文里一个混指了五节的词。** 第九节 Must#1 自 V1.1 起写
「文档上传 → **准入审核** → 解析分块 → 多存储落库」，但从未定义这四个字指什么：

| 读法 | 实现状态 | 后果 |
|---|---|---|
| 机械准入（格式/长度/元数据/重复） | **一直有**（`AdmissionRejected`，M1 就验过） | 什么也拦不住未复核内容进答案 |
| 人工复核（知识准入的最后一道闸） | **没有做成闸**：版本一上传即 `effective`，复核只是事后撤销 | 见下面的实测 |

**实测（2026-10-12，`scripts/m4_upload_http_check.py`，独立 scratch 库+集合+端口 38001，生产 193/24 未动）**：
以 `delivery_engineer` 上传一篇未复核文档后，复核**之前** `POST /retrieval/search` 命中该块，
`POST /answers` 直接返回 `status=answer` 并把那条未复核的块作为引用给出
（结论「心跳连续缺失 3 次即开工单；工单 30 分钟内响应」）。
**任何有写权限的角色（delivery_engineer / pm / presales_architect / knowledge_owner / system_admin）
灌一篇进去，下一次问答就可能引用它作答**——第十节约束里「数据不出域、密级隔离」拦得住读，拦不住这个。

**裁决 C（用户选定，本轮已实现）**：

1. **章落在版本上**，不落在文档上。新增 `document_version.reviewed_by / reviewed_at`，
   与 `effective/superseded` **完全分开**——回滚、下线都不该顺手把章擦掉；
   章若在文档上，一次复核就自动放行该文档以后所有新版本，**那正是投毒要防的形状**。
2. **闸装在答案层，不在检索层**：未复核版本**照旧可被检索**（复核人必须看得见内容才能判断能不能复核），
   但不进答案的证据面；证据被摘光时走**既有**的「无充分依据」拒答出口，不新造一条路径。
   对外只可以说一句**可实测的**话：「未经复核的内容不会被引用作答」——不能说「不会被检索到」。
3. **存量回填**：迁移时把 24 个既有版本一次性标成 `migration:pre-review-gate`。
   不回填就等于让现有语料一夜之间全部「答不出」，那是**断服务不是加闸**；
   回填身份写死在值里，审计上一眼能看出这章是迁移给的、不是谁复核的。
   迁移包在 `DO $mig$` 里判列是否存在，**幂等**（连跑两次不重复回填、不清章）。
4. 为什么不选 B（未复核不进索引）：B 才是字面意义上的「入库有闸」，但它把**复核延迟转嫁成知识不可用**，
   还要改对账口径（权威源含 pending、索引不含，天天报 `missing_in_vector`）——那是已经验过的机制，
   为一句更好听的话去动它不值。

**验收**：真机 14/14（含「复核前可检索但不进答案」「复核后两者皆可」两条成对断言，
`var/gate0/m4_upload_http.json`）；防回归 8 条（`tests/test_review_gate.py`，
其中「按版本摘不是按文档摘」那条直接钉住第 1 点）；全量单测 174 passed；
`verify_m4` 经 Nginx 12/12 复跑（加闸之后在线交付层没有回归）。
