3. **检索门禁 P95 334ms 距 800ms 有一倍余量**，这一格与 7B 无关，历来是这张表里最结实的一条。

## 二、协议（写死在产物里，否则下次换一套就又得到一个数）

- **走生产入口**：宿主 API `POST /api/v1/answers` 与 `POST /api/v1/answers/stream`，**不 in-process 调引擎**。
  in-process 的数不含 HTTP/序列化/审计落库那一截，等于换了个被测系统。
- **一问一 session**：`session_turn` 全表混着 verify/probe/前端走查自己打的流量，
  那张表的 p50/p95 是「这台机器这段时间所有流量的分布」，不是「用户点一次发送等多久」。
  统计只取**本次创建的 session_id**（100 行都是）。
- **冷启动单列**：模型首次装载单独记，不与热态混在同一个分位数里。
- **串行不并发**：8GB 显存下并发会把装载排队算进延迟。
- **起跑前清 Redis 检索缓存**（这一条是本轮现学的，见第三节 ②）。
- **先归档再动手**：`var/gate0/pre_reprobe/`（含 `m3_confidence_probe.json` 与其派生产物）——
  因为 67 行 `answer_correct` 人判标签是照着那份探针的 conclusion 逐条判的，**探针一重跑就覆盖源文件**。

**环境有多干净，当时就记下来了**（`env_at_measurement`，逐轮）：

| 轮 | GPU 占用 / 显存 | 非 KEE 容器 | 「cold_start_ms」这一栏的真实含义 |
|:---|:---|:---|:---|
| run2 | 13% / 5139 MiB of 8188 | `[]` | **真冷**（7B 未驻留）17164.3ms |
| rep1 | 8% / 7666 MiB | `[]` | 模型已驻留 → 3703.8ms，**不是冷启动** |
| rep2 | 1% / 7674 MiB | `[]` | 同上 3512.1ms |
| rep3 | 8% / 5139→7666 MiB | `[]` | 同上 4089.2ms |

⚠ 后三行的 `cold_start_ms` 字段名在这几轮里是**误导性的**——脚本每次先用第一题探一次，
模型已驻留时那一次只是「第一题的热态耗时」。**只有 run2 那一行是真冷装载**，对外引用冷启动只能引 17164.3ms（或转录轮的 23507.8ms）。

**做不到零背景**：IDE 与桌面服务就在跑（我就在里面）。已把当时的 GPU 占用与容器清单记进证据，
所以这两周的读数能不能信，判断权留给以后的人而不是留给我的记忆。

## 三、三件顺带查出来的事（比延迟数本身值钱）

### ① 拒答/转人工轮次**根本没有 `total_ms`** ⇒ 历史分位数全在悄悄丢最快的那些轮

`e2e_ms` 原先只在 `generate` 节点里写。不进生成的路径（敏感早退、检索门禁拦下、契约失败）
一个耗时都没记，`session_turn.total_ms` 落库成 NULL。后果不是「少几行数据」而是**系统性偏差**：
任何 `WHERE total_ms IS NOT NULL` 的 p50/p95 都在**只算慢的那些轮**，而且没人会注意到。
此前那份被引用过的「n=205 / p95 20700ms」就是这么算出来的。

- 修法放在图的**唯一出口** `src/kee/qa/graph.py::result_from_state`，而不是在每个提前 return 的节点各补一遍。
- 回归测试 `tests/test_qa_graph_stream.py::test_every_exit_path_carries_e2e_ms`（三条早退路径 + 生成路径）。
- 本轮核对：**100 个轮次里缺 `total_ms` 的 0 行**（每轮固定跑 6 道不进生成的题，就是为了让这件事可核对）。

### ② 检索缓存会**伪装成性能改善**——我第一次把它读成了「噪声真大」

`SearchCache`（Redis，TTL 300s）命中时**整条检索腿被短路**，`retrieval_ms=0.0`。
一轮 20 题约 2 分钟，于是**第二轮跑同一批题必然全在 TTL 内**：p50 从 3193ms 掉到 2947ms、
`retrieval_only` 的 n 直接变成 0。我当时的第一反应是「这台机器噪声真大」，其实是**换了被测系统**。

现在：`m5_latency_clean.py` **默认起跑前清缓存**（`--keep-cache` 才保留），SSE 段跑前再清一次
（同题刚被端到端跑过），且**所有端到端分位数只取未命中缓存的轮次**，命中的单列不合并：

| 分层 | n | p50 | p95 |
|:---|:---|:---|:---|
| 未命中（主口径） | 100 | 3242.2ms | 4242.5ms |
| 命中缓存 | 4 | 2707.9ms | 2731.7ms |

顺带给出一条**更正**：我此前说过「同配置两轮 p50 差 20%」——其中一轮的差别是缓存，不是噪声。
**真正的延迟噪声地板是清缓存后四轮之间的 p50 极差 93.6ms**（3193.4 / 3206.0 / 3287.0 / 3261.3）。
小于它的 Δ 不得写成「改善」或「恶化」。

### ③ 生成不可复现：重跑一次 ⑤ 探针，67 行里 **5 行结论文本变了**（7.46%）

同题、同配置、同权重，`conclusion` 换字的有 q-001/q-002/q-031/q-040/q-071 五行。
这与人判重标的 ~10% 行翻转噪声地板**同一量级**——所以「重跑一次看指标动没动」这件事，
在 7B + T=1.0 上本身就带着 7% 左右的自由度数。

后果是**配对纪律**：人判标签只能配**它判过的那一代产物**。
`m5_answer_correct_calibration.py` 因此加了 `--probe`，并在 qid 集合对不上时**拒绝产出**
（新题 q-080 没标签 → 拒绝 + 要书面理由 `--ignore-qids/--ignore-reason`，不静默跳过）。

按 `pre_reprobe/` 那份配对复算，**读数原样复现，未因重跑而变**：

| 人群 | n | accuracy | mean_conf | ECE | AUC | 结论 |
|:---|:---|:---|:---|:---|:---|:---|
| `answer_prod`（status ∈ answer/tentative） | 62 | 0.9677 | 0.7671 | **0.2006** | 0.7833（CI 0.6271–0.9138） | **>0.10 不达标**（欠置信） |
| `all_behav`（全 67 行，误拒/误转人工计 0） | 67 | 0.8955 | 0.7099 | **0.1857** | 0.9381（CI 0.8355–1.0） | 同上；高置信带内漏 2 行（q-013/q-076） |

新探针那代另给一个**代理**读数（不可与上表互换引用）：L4「ref 数字全对」acc 0.451 / ECE 0.3872；
成分判别力 AUC 仍全线无预测力（composite 0.3207、retrieval 0.2997、self_assessed 0.5031、n_citations 0.486）。
温度两档**依旧拒绝采纳**：`answer_prod` 负类仅 2 例不可辨识；`all_behav` 的 7 个负类里 5 行是拒答，
其复合分被规则**钉死为 0.0**，T<1 的收益几乎全来自把这批行更狠地压到 0——那是拟合
「没作答当然不算答对」这条同义反复，不是校准。运行时维持 T=1.0、复合分不进门禁。

## 四、为什么 M4 那条「1.2s 达不到」要作废

不是因为新数好看，是因为**旧数测的是另一个东西**：

| | M4 那轮 | #56 这轮 |
|:---|:---|:---|
| 入口 | `m4_stream_probe.py`（当时未记缓存状态） | 生产入口 SSE + **流前显式清缓存并记进产物** |
| 背景 | 本机还跑着别的容器与宿主应用 | auscult 一套已停，非 KEE 容器 `[]`，GPU 占用逐轮记录 |
| 读数 | 首个可见内容 p50 1642.7ms / p95 1960.4ms | 首个可读字 p50 695.4ms / p95 859.2ms / max 1008.6ms |

差 2.3 倍。**方向上对系统不利的那个口径（最严的首个可读字）我都取了**，仍然达标；
信封首字节 324ms 那个更宽松的值我同样报出来，但**不用它当判定依据**。

⚠ 这一格剩下的只是**文档措辞**：DoD 文字要不要把「首 token」钉成 `first_visible_ms`。
不钉，下次就有人拿信封那 324ms 对外说「首 token 0.3s」——那是择优取样本的一种写法。

## 五、仍未关闭的（本轮不声称解决）

1. **端到端 3s vs 6s 待用户裁**——本文只给依据，不代裁。裁 3s 的代价是实现改动，裁 6s 的代价是三件套改原文。
2. **ECE 敞口未闭**：0.2006 > 0.10，且按层归因后 7 行错行为**没有一行是校准能救的**
   （4 检索漏召 / 1 判定层 / 1 生成层 / 1 证据层）——这一格的状态仍是「测了且不达标」。
3. **无答案 7 + 敏感 5 共 12 题仍无真人标签** ⇒ 「该拒却答了」这半边（真幻觉率）仍只有代理读数。
4. **本机做不到零背景**：IDE 与桌面服务常驻。这批数比历史读数干净，但不是实验室意义上的净环境。
5. **q-063 这道无答案题 7.8s** 是含拒答口径下唯一的 >6s 样本，机制未查（拒答路径为何这么慢）。
6. 检索缺口（口语化查询与书面证据词法不重合，q-044 排名在噪声级别）——另列 #58。
