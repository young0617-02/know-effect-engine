## 这张表暴露的**口径互相打架**（M5 必须先裁，否则「达标」无定义）

1. **P95 完整答案 / 端到端**：DoD#5 写 `< 3s`，《项目定义》第六节写 `< 6s（Gate 0 实测后修订）`，技术方案 8.1 写 `< 6s`——三处两个值。**#56 净环境复测后这一条从『两边都过不了』变成『一边过一边不过』**：四轮合并 p95 4118.8ms ⇒ <6s 过、<3s 不过（68.42% 的轮次超 3s）。所以剩下的**只是口径裁决**：裁 3s 就要改实现（当前生成预算下不可达），裁 6s 只需按三件套把 DoD#5 的原文改过来。
2. **首 token 1.2s**：门禁值在、口径没定（信封首字符 / 首事件 / 首可见内容三种读法差一个数量级）。#56 已把三种读法**在同一次 SSE 跑里都量了**（n=24）：信封与首事件 p50 324.0ms、首个可读字 p50 695.4 / p95 859.2 / max 1008.6ms。结论：**取最严的那把也达标**，这一格不再需要裁「认哪个口径」——需要裁的是 DoD 文字要不要把口径写死，免得下次有人拿信封那 324.0ms 对外说『首 token 0.3s』。
3. **「引用正确率」到底指什么**：DoD#3 的 ≥ 90% 原来只有「引用落 gold」一种实测，它不等于结论正确。**2026-10-12 起这一格有两种实测并存**（落 gold 0.9839 / 人判 answer_correct 0.9677），判据文字仍写「引用正确率」——两个数都能自称 ≥ 90%，但说的不是同一件事，**M5 要裁的是把哪个钉成门禁**，建议裁成人判那一列（它才是用户收到的东西）。
