# M4 · 流式交付实测（token 级流式已实现并覆盖全量答案，但没达到 ① 的门禁）

> **口径声明**：本文数字是本次真机实测值（RTX 4060 8GiB / 本地 `qwen2.5:7b` / 模拟语料 24 篇 193 块，58 道可答题）。
> 语料含模拟件，绝对值只代表「达成路径是否存在」，不构成上线承诺。

跑法：`uv run python scripts/m4_stream_probe.py`，证据 `var/gate0/m4_stream_probe.json`。

---

## 一、结论先说

token 级流式**做出来了、覆盖住了、也是安全的**，但它**没达到 ① 留给它的门禁**，差约 0.4 秒。

| 指标 | 实测 | 门禁 / 参照 |
|---|---|---|
| 有可流内容的题 | **54/58 = 93.1%** | 未覆盖的 4 题全是 `refuse`——本来就没有答案可显示，所以**按「答出来的题」算是 54/54 = 100%** |
| 首个**可见内容** p50 / p95 | **1642.7 / 1960.4 ms** | 首 token < 1.2s → **只有 1.85% 达标** |
| 信封首字符到达 p50 | 849.5 ms（92.6% 低于 1.2s） | **这个数不能用**，见第二节 |
| 首个事件（含检索，骨架先到） | p50 **440.4 ms** | 这是前端能真正开始渲染的时刻 |
| 结论级撤回 | **0/54** | 流出的结论最终都成了答案 |
| 条目级丢失（要点被引用强制丢弃） | **0** | 见第四节，这个 0 是语料性质，不是设计保证 |
| 流式 vs 非流式最终响应 | **10/10 结构一致** | 两条交付方式没有分叉 |

**要落地就得承认的一件事**：这条链路真正的进度信号是「440ms 出检索骨架」，而不是「1.6s 出第一个答案字」。
本地 7B 面对几千字证据提示词，prompt eval 本身就在秒级——1.2s 这条线在「首个可见答案字」这个口径下**达不到**。
**门禁我没有动**（① 的条款，改它走 3.4 回退分支，是裁决不是实现）。

---

## 二、那个会让人误会的数字

`信封首字符 p50=849ms、92.6% 低于 1.2s` —— 照这个数报，token 级流式**看起来**过了门禁。

它测的是生成层吐出第一个字符的时间，而 JSON 模式下那个字符是 **`{`**。屏幕上什么都没有。
所以探针同时记两个数，并在 `first_token_ms` 里写了 `warning` 字段：
**报门禁必须用可见内容的时间**，否则就是拿协议层巧合冒充答案的开始。

---

## 三、为什么要连 `key_points` 一起流（覆盖率 20.7% → 93.1%）

第一版只流 `conclusion`，实测**只有 12/58 = 20.7% 的题有可流内容**：
其余 79% 的结论是 M3-01c 逐字搬运拼出来的，模型自己没写 `conclusion`。

也就是说 **把完成率从 24% 修到 91% 的那个修法，正是让 token 级流式失去用武之地的原因**。
两件事不冲突，但只看「完成率 91%」会误以为流式覆盖 91%。

改为同时流 `key_points[].point`（要点文字确实是模型生成的）后覆盖率到 93.1%，
未覆盖的 4 题全是合法拒答。前端渲染顺序上，要点先于搬运结论出现，
与「答案正在成形」的观感一致。

---

## 四、0 撤回这件事，不能当保证

本轮 `provisional_retracted=0/54`、`provisional_lost=0`。**但这两个 0 都有具体原因，不是安全性的证明**：

* 引用强制在这份语料上**一个要点都没丢过**（Gate 0 与 M3 各轮实测 `points_dropped_total=0`）——
  因为模型给的 `evidence_ids` 一直落在本次检索集合内。
  也就是说「要点被丢弃导致用户眼前的文字消失」这条路径**从未被执行到过**。
  所以 `lost_items` 这个字段是**埋的探针，不是已经量出为 0 的风险**。
  构造用例（`tests/test_qa_token_stream.py`）确认过：一旦要点全被弃，`provisional_retracted` 会正确翻成 True。
* 撤回在设计上是可能的，因为**引用强制必然晚于流式**。所以字段留着：
  `delta` 一律带 `provisional: true`（前端必须用未完成态渲染），
  `answer` 带 `provisional_retracted` / `provisional_lost` / `provisional_lost_samples`，持续量而不是量一次。

## 五、实现与测试

| 件 | 说明 |
|---|---|
| `OllamaClient.chat_stream()` | NDJSON 逐段；`("delta",片段)` / `("final",LlmResult)` / `("error",说明)`；metrics 与 `chat()` 同构（含 `done_reason`） |
| `kee/qa/stream_json.py` | 从未闭合信封里按**路径**读字符串值：`("conclusion",)`、`("key_points",0,"point")`。键/值靠帧状态判定不靠猜；标量「消费但不产出」，否则数组下标错位 |
| `kee/qa/streaming.py` | 图跑在工作线程，事件经队列出来（同线程做不到既阻塞跑图又逐帧发事件） |
| `graph.generate` | **流式与非流式共用同一个节点**：同一张图、同一套出口契约。回调经 state 注入而非挂 engine——引擎实例跨请求复用，挂上去会把上一请求的管道接进下一请求 |

测试 **157 项**（本次新增 20）：

* 扫描器 13 项，核心是一条**性质**：对完整输出的**每一个前缀**，扫出的值必须是对应最终值的前缀。
  它抓到过两个真 bug：① 缓冲停在 `{"conclusion":` 时把「还不知道」报成「确定不是文本」，
  结论区会被短暂判死；② 要点若按到达顺序排，中间项缺席时会把后一条安到前一个序号上——
  那是显示错内容，不只是不好看。
* 流式行为 8 项：事件序、每个流出的字段都是它最终内容的前缀、要点流带来覆盖率、
  撤回判定含「要点全被弃」的构造用例、开关关闭退回阶段级、生成失败仍以 answer 收尾而非让前端停在半路。
* 探针自带有效性前置（`kee.eval.probe_guard`）：依赖宕机会伪装成「整齐的 degraded + 空结论」，
  那时撤回统计会是 0、看起来像安全。判废即不写 artifact。

差分网仍 **18 场景 0 未声明差异**——流式改造没动到控制流语义。

## 六、待裁决

1. **① 的「流式首 token < 1.2s」怎么处理**：按可见内容实测 1.85% 达标。
   要么改口径（例如按「首个事件（含检索）p50 440ms」这类骨架进度信号判），
   要么承认本地路径达不到、把 1.2s 降为报告值。**这条要我改门禁得走 3.4 回退分支。**
2. **`token_stream` 默认值**：现在默认 `true`。覆盖率 93.1%、无额外生成开销、0 撤回，
   默认开已经站得住；但答案首字比门禁慢约 0.4s，若不接受这个事实就该默认关并显示骨架。
