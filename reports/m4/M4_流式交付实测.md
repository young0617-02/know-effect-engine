# M4 · 流式交付实测（token 级流式已实现，但没达到它要达到的门禁）

> **口径声明**：本文数字是本次真机实测值（RTX 4060 8GiB / 本地 `qwen2.5:7b` / 模拟语料 24 篇 193 块）。
> 语料含模拟件，绝对值只代表「达成路径是否存在」，不构成上线承诺。

跑法：`uv run python scripts/m4_stream_probe.py`，证据 `var/gate0/m4_stream_probe.json`。

---

## 一、结论先说

token 级流式**做出来了、也是安全的**，但它**没有达到 ① 留给它的门禁**，而且
**只能覆盖两成答案**。两个理由各自独立，任一都足以让它默认开着但没有实际收益。

| 指标 | 实测 | 门禁 | 判定 |
|---|---|---|---|
| 有可流结论的题占比 | **12/58 = 20.7%** | — | 其余 79% 模型没写 `conclusion`，无内容可流 |
| 首个**可见结论字** p50 / p95 | **1442.3 / 1767.0 ms** | 首 token < 1.2s | **0/12 低于门禁，即 0% 达标** |
| 信封首字符到达 p50 / p95 | 868.3 / 1199.3 ms | — | 94.4% 低于 1.2s——**但这个数不能用**，见第二节 |
| 撤回率（流过文字后未成为答案） | **0/12** | — | 正面：provisional 风险本轮未兑现 |
| 流式与非流式最终响应一致性 | **10/10 结构一致** | — | 两条交付方式没有分叉 |

## 二、那个会让人误会的数字

`信封首 token p50 = 868ms，94.4% 低于 1.2s` —— 如果照这个数报，token 级流式**看起来**过了门禁。

它测的是生成层吐出第一个字符的时间，而 JSON 模式下那个字符是 **`{`**。
屏幕上此时什么都没有。所以这条实现真正的用户可感知量是「第一个结论字到达时间」，
实测 p50 **1442ms**，**12 题里没有一题低于 1.2s**。

这不是实现缺陷，是**本地 7B + 几千字证据提示词的 prompt eval 就在这个量级**——
把 `{` 记成首 token 是协议层的巧合，不是产品层的进度。
**报门禁时必须用可见内容的时间**，否则就是拿一个字符的到达冒充答案的开始。

---

## 三、为什么只有 20.7% 能流——以及这件事和 M3-01c 直接相关

79% 的题 `conclusion` 字段是空的，答案文字来自 **M3-01c 的逐字搬运**
（把 `key_points` 拼成结论；实测 39/58 走这条路，见 M3 报告第四节）。
模型没写结论，就没有 `conclusion` 可流——那些题只能等 `answer` 事件。

**也就是说：把完成率从 24% 修到 91% 的那个修法，正是让 token 级流式失去用武之地的原因。**
两件事不矛盾，但必须一起看：单看「完成率 91%」会以为流式能覆盖 91%，
实际覆盖的是模型自己写结论那 12 题。

由此有两条可走的路，都还没做，需要定：

* **A. 连 `key_points` 一起流**。要点文字确实是模型生成的，流出来就能覆盖那 79%。
  代价：扫描器要从「顶层字符串字段」扩展到「数组内对象的字段」，是新增正确性风险面
  （现有的性质测试要跟着扩），且要点是碎片、逐条出现，前端要处理「答案还没成形但已经在长」。
* **B. 承认覆盖有限，把它当锦上添花**，只在模型自己写结论时流；`token_stream` 保留开关。
  这条不解决门禁不达标，只是不再假装。

## 四、已经确认为安全的部分

* **撤回率 0/12**：流过非空文字的题，最终都成了对外答案，没有「先显示后作废」。
  这条必须继续量而不是一次定终身——引用强制天然晚于流式，撤回在设计上是可能的，
  所以 `answer` 事件带 `provisional_retracted`，`delta` 一律带 `provisional: true`，
  前端**必须**用未完成态渲染（`kee/qa/streaming.py` 的模块说明写了为什么）。
* **两条交付方式不分叉**：流式跑的是同一个图、同一个 `generate` 节点、同一套出口契约，
  10 题对照的响应字段集合与状态一致性全通过。
  刻意**不比结论文本**——本地 7B 两次生成本来可能不同，比文本会把生成抖动误报成分叉。
* **单测 151 项**，其中 token 流式 8 项（事件序、流过的文字是最终结论的前缀、
  撤回判定、开关关闭时退回阶段级、首字延迟有记录点、生成失败仍以 answer 收尾）。
  增量 JSON 扫描器另测 8 项，核心是一条**性质**：对完整输出的每一个前缀，
  扫出的值必须是最终值的前缀（实现过程中扫出「以后会被改掉的内容」是不允许的）。
  这条性质测试真的抓到一个 bug：缓冲停在 `{"conclusion":` 时扫描器把「还不知道」
  报成「确定不是文本」，会让结论区在某一帧被短暂判死。

## 五、待裁决

1. **① 的「流式首 token < 1.2s」怎么处理**：按可见内容实测 0/12 达标。
   要么改门禁口径（例如按「首个事件（含检索）p50 431.9ms」这类更早、但只是骨架的进度信号判），
   要么承认本地路径达不到并把 1.2s 降级为报告值。
   **我没有动这条门禁**——它是 ① 的条款，改它要走 3.4 回退分支，是裁决不是实现。
2. 走 A 还是 B（要不要连 `key_points` 一起流）。
3. `token_stream` 的默认值：现在默认 `true`。按上面的覆盖率与达标率，
   默认开只在两成题上有意义，但也无害（不额外花一次生成）。是否改成默认关，等 A/B 定了一起看。
