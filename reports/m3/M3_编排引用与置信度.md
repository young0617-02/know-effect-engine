## 二、M3-01 「引用落 gold 仅 23.5%」是错的：真问题是空结论

Gate 0 ⑤ 之后，「检索 top-5 有 gold 占 98%，但模型实际引用落在 gold 上只有 23.5%」这句话
被写进了 `reports/gate0/`、《技术方案》V1.0.2 修订记录、《项目定义》V1.2 修订记录，
并据此把「引用落点对齐」定成 M3 的头号任务、把 ECE 0.374 的根因解释成「置信度取检索分而标签取引用落点」。

**这次把入库的原始证据 `var/gate0/g05_citation_calibration.json` 逐行重算，结论是：那个 23.5% 不是引用落点率。**

### 证据链（全部可复算，不需要跑容器）

`g05_citation_calibration.py:41` 的标签定义是三个条件的合取：

```python
correct = int(res.status in ("answer","tentative") and bool(res.conclusion) and bool(cited_ids & gold))
```

而 `citation_hits_gold` 只记第三项。把 51 个可判答案行（`expected_behavior=answer` 且置信度含 logit）
按这两个字段分头统计：

| 指标 | 实测 |
|---|---|
| **行级引用落 gold**（`citation_hits_gold`） | **51/51 = 100%** |
| 条目级引用落 gold（58 条引用中至少 51 条命中；每行只记一个 0/1 位，故为**下界**） | ≥ 87.9% |
| `correct`（= 落 gold **且有结论**） | 12/51 = **23.53%** ← 报告里那个数 |
| 其中 `conclusion` 为空的行 | **39** |

`citation_enforcement` 段另有两个佐证：`answers_without_citation = 0`、`points_dropped_total = 0` ——
引用强制机制本身一次都没有触发过丢弃。

代码同一性已核：`src/kee/qa/answer.py` 自 `bbc4bfa`（2026-10-09，即 g05 那次运行）之后**没有任何提交**，
所以我读的代码就是产出这份 JSON 的代码，上面是推证不是猜测。

### 真正的缺陷：结构化输出契约没有被校验

39 行的形态是 **`no_evidence=false` + key_points 有 + citations 有 + `conclusion` 是空字符串**。
引擎全盘接受了它，还给了 `status=answer`（28 行）或 `tentative`（11 行）。

也就是说：**系统会对外返回一条「有出处、有要点、但没有结论」的答案，并标记为成功**。
这不是引用错，是契约漏检——而方案 6.3 要 LangGraph「类型化（Pydantic）状态」正是为了拦住这类不一致输出。

### 对 M3 计划的三处改向

1. **「引用落点对齐（23.5% → ≥90%）」这个遗留跟踪项作废**：引用落点实测 100%，没有 66 个点的缺口要补。
2. **新增 M3-01b：答案结构契约校验**——`status=answer` 必须满足 `conclusion` 非空且至少一条要点；
   违反即降级为 `degraded` 并转人工，不得以 `answer` 状态返回。这条要进类型化状态机的出口校验。
3. **ECE 0.374 的根因描述要改写**：标签 `correct` 里混着「有没有结论」这一项，所以它测的是
   「答案完整率」而不是「引用可信度」；置信度主项取检索分与之不同源的判断方向仍成立，
   但**归因文字必须改**，否则 M3-04 会照着错的因果去重定置信度成分。

### 顺带暴露的一个报告缺陷

`reports/gate0/g05_citation_calibration.md` 第 29 行的节标题写着「可靠性（**引用是否落在 gold 上**）」，
下面直接给 0.2353。而 0.2353 是 `answerable_hit_gold`（含结论条件）。同一份报告第 243–244 行
其实已经写了「两者不要混读」的警告，**但节标题自己就混读了**。已在该处加更正横幅。

## 三、M3-01b 答案结构契约校验（已落地并实测）

### 先做真机复现，再改代码

对 6 道 Gate 0 判 `correct=0` 的题在当前系统上重跑：

```
q-001 status=answer  concl_len= 0 n_cit=1 落gold=1 要点=1 | ''
q-005 status=answer  concl_len= 0 n_cit=1 落gold=1 要点=1 | ''
q-008 status=answer  concl_len=12 n_cit=1 落gold=1 要点=1 | '15 分钟内启动应急响应'
q-010 status=answer  concl_len= 0 n_cit=1 落gold=1 要点=1 | ''
q-011 status=answer  concl_len= 0 n_cit=1 落gold=1 要点=1 | ''
q-012 status=answer  concl_len= 0 n_cit=1 落gold=1 要点=1 | ''
```

**6 题里 5 题至今仍是「有要点、有出处、无结论却报 answer」**，缺陷是活的，不是历史遗留。

### 修法

`AnswerEngine` 出口加确定性契约校验，并按违规类型分流（分流语义刻意区分）：

| 违规 | 状态 | 是否转人工 | 含义 |
|---|---|---|---|
| 无要点 / 无出处 | `refuse` | — | 「没有可用依据」——这是我们对证据的判断 |
| 有出处但 `conclusion` 空 | `degraded` | **是** | 「依据在、但这条答案没做完」——不能冒充前者，也不能冒充成功 |

两条路径都**不写 `logit`**。这不是省事：可判校准集按 `logit` 是否存在来筛，
空结论若仍带 logit，ECE 就会被测成「答案完整率」——那正是 Gate 0 ⑤ 犯的错。

### 全量实测（58 道可判答案题，`scripts/m3_answer_probe.py`）

| 指标 | 结果 |
|---|---|
| 状态分布 | `answer` **14** / `refuse` 5 / `degraded` **39** |
| 契约拦下的空结论 | **39**（与 Gate 0 逐行重算推出的 39 完全吻合） |
| 仍被判 answer/tentative 且结论为空 | **0** |
| 行级引用落 gold | **53/53 = 100%**（再次独立确认第二节的更正） |
| 需人工复核 | 44 |
| e2e P50 / max | 4485ms / 11332ms |
| 可判校准集 ECE（n=14） | 0.1617（mean_conf 0.8383，accuracy 1.0） |

### 这组数字里最重要的一条，是它让指标变难看了

**加契约之前报「51 个成功答案」，之后就剩 14 个。** 真实的答案完成率是 **14/58 = 24%**，
不是原来读起来的 88%。39 条不是答错，是**根本没答完**——而系统一直在把它们计成成功。

同时必须写清：**ECE 0.1617 不能读成「校准变好了」**。它的可判集从 51 缩到 14、标签也从
「含结论条件的复合值」换成「引用是否落 gold」，与 Gate 0 的 0.374 **不是同一个量**，不可比。

### 反向验证（防测试自己失效）

临时把契约条件短路成 `if False and not conclusion:` 后重跑单测：**3 个新测试失败**，
复原后 88 项全绿、文件字节一致。测试确实在钉这个行为，不是空转。

### 遗留：39/58 的空结论本身还没修

契约只是**不再让它冒充成功**，没有解释模型为什么在有依据、有要点的条件下仍不写结论。
候选方向（都要单独测，不在本轮顺手改）：提示词里结论与要点的边界、`max_tokens` 是否被截断、
7B 在该任务上的服从率。**这条应作为 M3 的独立事项跟踪**，否则 24% 的答案完成率会被
「契约已生效」这个事实盖住。

## 四、M3-02 强证据却声明无依据 → 反向兜底（已落地并复跑 ⑤）

### 先把那条真实漏转找出来，不凭空定规则

Gate 0 ⑤ 期望 `escalate` 的 5 题里只有 q-070 漏转：

| 字段 | 值 |
|---|---|
| 问题 | 电子记录那个项目的**应急储备金比例**是多少，模板变更超量按什么**单价**结算？ |
| 期望 | escalate（机密商务口径，对外仅可提供总价区间） |
| 旧状态 | `refuse`，`needs_human=False` |
| 检索分 | **0.9683**（强证据） |
| 敏感词表 | `报价/合同金额/口令/账号/特权/付款…` —— **问题里一个都不含** |
| gold | `chm-presale…#3.1#c1/c2`，正文含「**报价**附注」 |

漏转的机制因此很清楚：**敏感性在证据里，不在问题里**，所以前置关键词规则接不住；
而模型拒答后 `n_citations=0`，「引用落密级 3 才转人工」那条后置规则也永远没机会触发。
两条规则之间正好漏掉这一类。

### 修法：分两层，第一层不需要任何阈值

| 层 | 规则 | 依据 |
|---|---|---|
| 1 | 声明无依据 → **一律** `needs_human=True` | 不需要阈值。知识服务里「查不出来」恰恰是最该被人看见的出口 |
| 2 | 且 `top_score ≥ 0.90` → 状态从 `refuse` 改 `escalate` | 此时 `refuse` 是在**断言一件检索层反对的事**（"没有依据"），不能这么报 |

阈值刻意**只用于决定状态措辞，不用于决定是否复核**，所以即使阈值不准，第 1 层仍兜得住。
阈值本身的诚实交代：该转人工的 q-070 是 0.9683，该拒答的 q-059 是 0.8745，**间隔只有 0.09、
负类只有 7 个样本**，0.90 是贴着观测间隔的上沿，不是验证过的分离点。

### 复跑 ⑤ 的结果（`var/gate0/m3_g05_recheck.json`）

| 机制 | Gate 0 原测 | M3 复跑 |
|---|---|---|
| 零引用结论 | 0 条 ✅ | 0 条 ✅ |
| 敏感/低置信必转人工 | 4/5，漏 q-070 | **5/5，`missed=[]`** ✅ |
| 无依据必拒答 | 7/7 ✅ | **6/7** ⚠️ |
| 结构化首次成功率 | 96.7% ✅ | 见 JSON |
| 留出集 ECE | 0.3743（n=26） | 0.0（**n=7，退化，不可读成校准变好**） |

**目标达成**：q-070 `refuse → escalate`，5 道敏感题全部转人工。

### 但 ⑤ 仍然判不通过，而且原因不是我调的阈值

退的那一格是 **q-061**，它变成的是 `degraded` 而**不是** `escalate` —— 也就是说
**跟 M3-02 的 0.90 阈值无关**（它检索分只有 0.2074，远低于阈值）。真正的链路是：
模型这轮对一道语料里确实没有答案的题**产出了引用**（`citation_hits_gold=0`）却没写结论，
于是被 M3-01b 的契约判成 `degraded`。

这里有一件必须挑明、且**不该由我自行改掉**的事：⑤ 的判定口径是
`correctly_refused_or_escalated`，不含 `degraded`。而 q-061 在两种口径下**都进了人工队列**
（`needs_human=true`），并没有把一条无依据的答案泄给用户。
所以「6/7 算不算漏」取决于门禁要不要把「已转人工的 degraded」计为安全出口。
**这是门禁定义的改动，列为待裁决，我在报告里仍按原口径记 6/7 不通过。**

### 复跑过程里差点踩到的一个副作用

`g05_citation_calibration.json` / `verdict_05.json` / 报告 md，复跑完把新产物另存为
`m3_g05_recheck.json` / `m3_verdict_05_recheck.json`，再 `git checkout` 复原历史三份，

（在 n=7 的退化集上拟合出来的），一并复原；M3-04 会在扩样本后重新标定。

## 五、M3-01c 答案完成率 24% 的根因：字段错位，不是没答案

### 先分型，四条互斥候选一次测清

`scripts/m3_conclusion_probe.py` 对 58 道可判答案题逐条记录 `done_reason`、token 数、
JSON 是否完整、`conclusion` 键是否存在，分成四类：

| 候选机制 | 实测 | 结论 |
|---|---|---|
| `truncated`（被 `num_predict` 截断，M2 改写踩过同型坑） | **0** | 排除。`done_reason` 全是 `stop`，tok 中位 127，远低于 700 |
| `parse_failed`（JSON 无效） | **0** | 排除 |
| `missing_field`（没有 conclusion 键） | **0** | 排除 |
| **`empty_field`（键在、值为空串）** | **45/58 = 78%** | **就是它** |

而且这 45 条**全部带非空 key_points**，两组的输出 token 数中位数 127 对 131 几乎相同 ——
模型不是没力气写，是**把答案写进了另一个字段**。看原文最直观：

```
q-001  {"conclusion": "", "key_points": [{"point": "银企直联实时清算方案 V3.2 的灾备切换目标按 RTO 小于 15 分钟设定", ...
q-005  {"conclusion": "", "key_points": [{"point": "人行支付报文字段共改造报文字段映射 214 项", ...
q-010  {"conclusion": "", "key_points": [{"point": "…遥测数据上送覆盖…共 14 个测点", ...
```

要点本身就是完整答案。所以这是**字段错位**，不是「模型答不出来」。

### 提示词根因

`USER_TEMPLATE` 的 schema 字面写着 `"conclusion": "一句话结论（无依据则空字符串）"`，
`SYSTEM_PROMPT` 规则 2 又把「conclusion 留空」作为合法状态说了第二遍。
模型被**两次告知留空是允许的**，而没有任何一处说明 conclusion 与 key_points 必须同时非空、且不可互相替代。

### 我按这个根因先改了提示词，然后测出它更坏 —— 已回退

改成「形态A：no_evidence=false 时 conclusion 不得为空」后：

| 指标 | 改提示词后 |
|---|---|
| 可判答案完成率 | 13/58 → **58/58** |
| 语料内确实无答案的 7 题中给出结论的 | 0/7 → **2/7** |

q-059 现在输出 `status=tentative`、`needs_human=False`、结论 35 字：
**「该项目的终验结论于2024年12月20日出的，一次通过率为93.7%。」** —— 一道语料里没有答案的题，
被编出了一个带具体日期和百分比的答案，还带 1 条引用，而且**没有转人工**。

「要求结论非空」是在向模型施压产出它原本不愿产出的东西，而空结论原本是模型表达不确定的出口。
**把「该答不答」换成「不该答也答」，对知识服务是严格更坏的方向**，所以提示词已回退到原样，
并在代码里留注释记录这个负结果，防止下一轮又有人「顺手改提示词」。

## 六、M3-03 问答端点与流式契约（已落地）

此前 API 里**根本没有任何问答端点**（只有 documents / retrieval/search / reconcile / healthz），
Must#3 与 Must#7 无法对外验证。

### 新增

| 端点 | 说明 |
|---|---|
| `POST /api/v1/answers` | 结构化答案（结论 + 要点 + 出处 + 置信度 + 免责），支持 `session_id`、`Idempotency-Key`、`rewrite` 开关 |
| `POST /api/v1/answers/stream` | SSE，**阶段级**事件 |
| `GET /api/v1/sessions/{id}` | 会话轮次历史 |

新增 `session_turn` 表（轮次号在会话内单调递增，用 `INSERT ... RETURNING` 而不是先查后插以免并发撞 UNIQUE）。
会话状态放 PG 而不是 Redis：本项目口径是「其余存储皆可从权威源重建」，
会话若只能从缓存恢复就等于会丢；M3-05 的 LangGraph Checkpointer 也接这张表，不另起一套状态。

### 两处刻意的设计决定

**1. `skip_embedding` 下答案端点直接 503，不降级成 sparse-only。**
降级在功能上「能跑」，但会把检索质量悄悄换掉 —— 那种静默替代比明确失败更危险。

**2. 流式是阶段级，不是 token 级。** 这里暴露了方案内部的一条冲突：
⑤ 的门禁要求「只输出 JSON」以保证结构化首次成功率，而**未闭合的 JSON 片段前端无法渲染**，
所以「流式首 token < 1.2s」与「只输出 JSON」这两条要求本身互斥。
要做 token 级流式必须改成两趟（先流式自由文本、再结构化），那会牺牲结构化门禁。
**这条列为待裁决**，本轮先把能做实的部分做实：检索约 350ms 即出事件，前端可立刻展示证据骨架。

### 建表时机的一个坑

`session_turn` 加进 `SCHEMA_SQL` 后问答端点仍报 `relation does not exist` —— 因为
`init_schema()` 只有摄取路径会调，答案路径从不调用，**等于问答端点依赖了一套只有别人会建的表**。
修法不是把它挪到 `create_app`：那样 PG 挂掉时应用根本起不来，`/healthz` 就没办法回答「依赖挂了」，
启动期硬连依赖会把可观测性一起带走。改成**首次问答时惰性建表一次**，失败不抛，
让后面真正用到表的语句自然出 E901，那才是准确的信号。

### 我自己写出来的一条假绿，以及怎么抓的

第一版 RBAC 步骤断言「新人引用密级 ≤ 1」，而那次新人恰好是 `refuse` 零引用，
`max(..., default=0) <= 1` 空转就过了 —— **什么都没测**。

不成立就判失败而不是放行，因为「双方都拒答」证明不了任何过滤在起作用。

### 端到端 10 步全绿（`scripts/verify_m3.py`，证据 `var/gate0/m3_verify.json`）

依赖就绪 → 单轮结构化答案 → 每条引用带 doc/章节/页 → 同会话轮次递增 → 历史端点 →
幂等重放不增轮次 → RBAC 非空转对照（Owner 引到密级 2 并答出「正反向隔离装置单向传输」，

## 七、M3-04 置信度成分与判定标签同源化（诊断完成，方向已裁决落地，待真机复跑）

两条结论都推翻了我此前的说法，所以先记账，处置方向留给你裁决（涉及方案 6.4 的 Must 级设计）。

### 一、Gate 0 那条「ECE 0.2422」和「状态分布 answer 42」都不是服务路径的读数

**证据 A：所有基于 gold 的标签在这份语料上全是零方差。**

| 标签 | 可判集上的取值 |
|---|---|
| L1 任一引用 ∈ section gold | **53/53 全为 1** |
| L2 任一引用 ∈ strict gold | **53/53 全为 1** |
| L3 引用落 strict gold 的比例 | 52/53 = 1.0（只有一个不同） |
| L4 结论含齐 ref 全部数字 | 21/44 为 1，均值 0.681，10 个不同取值 ← **唯一有方差的** |

gold 层级的标签测不出差别，是因为引用强制已经保证「要点必须挂证据、证据必须在本次检索集合内」，
而检索 top-5 的命中率高到「任一条落 gold」几乎必然成立。
所以 ECE 在这个标签上没有可校准对象，它算出来的就是 `|mean_conf − 1.0|`。

**证据 B：置信度公式 93% 是常数。**

| 成分 | 权重 | 可判集上的分布 | AUC（对 L4） |
|---|---|---|---|
| `retrieval` | 0.45 | 均值 0.8911、79% ≥ 0.9（M2 已发现的 reranker 饱和） | **0.319** |
| `citation_consistency` | 0.35 | **常数 1.0（53/53）** | 无定义 |
| `self_assessed` | 0.20 | 只有 {0.0, 0.9}，均值 **0.034** | 0.524 |
| `composite` | — | 0.4588–0.9780，均值 0.7578 | **0.346**，bootstrap 95% CI (0.194, 0.512)，96.5% 重采样 < 0.5 |

`0.45×0.89 + 0.35×1.0 + 0.20×0.03 = 0.758` 与实测均值分毫不差——
也就是说 composite 里**只有检索分在动**，而那一项在这批数据上是**低于随机**的。
`n_citations`(0.526) 与 `evidence_number_count`(0.501) 这些替代候选也一样在 0.5 附近。

**证据 C：T=6.655 不是校准，是把分数抹平。**
`fit_temperature` 的粗网格上界是 5.0，但三轮细化把 T* 推到 6.655 —— 因为 L4 的正类率是 0.477≈0.5，
NLL 在无信息分数上的最优解就是「全体输出基率」（T→∞ 时 sigmoid(z/T)→0.5）。
**这不是校准器在工作，是校准器发现没有可校准的东西。**

已给 `fit_temperature` 加零方差拒绝（返回恒等 T=1.0 并带 `refused`，让调用方拿不到一个可以冒充
拟合成果的数字），配两条单测，并**反向验证过它不是恒真断言**：把守卫临时删掉，
测试立刻失败在 `assert 0.05 == 1.0` —— 复现出来的正是当初坑过我的那个 T=0.05 退化值。

**证据 D：服务路径与离线探针跑的是两套温度。**
API 从 `calibration.json` 读 T=6.655，而 `m3_answer_probe.py` 用默认 T=1.0。同一批 58 行重算：

| 温度 | 可判答案状态分布 |
|---|---|
| T=1.0（我此前报的数） | `answer` 42 / `tentative` 11 / `escalate` 5 |
| **T=6.655（API 实际在跑的）** | `answer` **0** / `tentative` 53 / `escalate` 5 |

服务温度下 `calibrated` 的**可达上界只有 0.6388**，而 `answer` 门槛是 0.75 ——
**结构上永远够不到，`answer` 这个状态对外从未出现过。**
（完成率 91% 不受影响：它按「结论非空」判，53 这个数与温度无关。受影响的是状态分布与 `answer` 可达性。）

### 三点五、顺手把 ⑤ 最后那条漏拒收掉了（M3-04b）

q-061 的链路是：`top_score=0.2074`（比检索门槛 0.20 只高 0.0074）→ 模型给了 1 条有效要点、
**结论留空、自评 0** → 逐字搬运替它拼出结论 → 低置信转人工。于是「无依据必拒」少 1。

这里有个必须先说清的歧义：**转人工的行上带着结论串，算不算违反「无依据必拒」**？
我按严格解读处理（不算也要当成不算），因为严格侧对两种理解都安全——
不补结论后它是 `refuse` 且无要点无引用，无论口径怎么定都不构成漏拒。

**规则不是新造阈值，而是复用分档门槛**：只有当 `composite ≥ confidence_low` 时，
空结论才按「字段错位」搬运；低于它，说明**证据、模型自评、模型是否写结论三个信号同时不确定**，
此时由我们把要点拼成结论，就是替模型说一条站不住的话。
搬运判据与分档判据共用同一个 `composite_score()`——两处各算一遍迟早会长成两个「置信度」。

**安全性是核过的，不是假设的**（对已入库的 `m3_answer_probe.json` 58 行离线重算）：

- 带 `conclusion_derived_from_points` 标记的 **39 行，无一低于 0.45**；
- 可判集 composite 下界是 **q-046 的 0.4588**，q-042 的 0.4719；
- 所以搬运下限落在 0.45，正好在**最近一条合法行的下方**。

但必须同时写下：**余量只有 0.0088。** 这不是一个稳健的分隔，是贴着观测边界画的线。
下次真机跑出一个 composite 落在 0.44–0.46 的行，它就会从「搬运答出」翻成「拒答」，
完成率随之少 1。所以这条属于「知道它薄、并且能看见它翻」的状态，不是「已解决」。

验证：3 项新单测（含一条反向对照——只抬高证据强度，搬运必须照常发生，
否则上一条测试可能只是「搬运被整个关掉」而把完成率打回 24% 无人察觉）。
**反向验证做过**：临时禁用下限，两条断言立刻失败（第三条按设计仍通过，它测的是反方向）。
差分网加到 **18 场景**，其中场景 18 是**已裁决的故意不等价**——脚本正向断言两边形状

## 八、M3-05 LangGraph 类型化状态机 + 多轮指代消解（已落地，真机已复跑）

`src/kee/qa/graph.py`（370 行）+ `src/kee/qa/answer.py`（189 行的 `answer()` 压成 26 行委托）。

### 实际拓扑与方案 6.3 的草图不同，且是有意为之

```
START → sensitive_gate → rewrite → retrieve → retrieval_gate → generate → enforce → confidence → END
          └─ gated ────────┴─ gated ────────────┴─ gated ────────────────────────────┘
```

方案 6.3 画的是 `查询改写 → 混合检索 → 重排 → 生成 → 引用校验`，没有敏感闸，也没有把「检索不足」
和「答案不成立」分成两道门。三点差异：

| 差异 | 理由 |
|---|---|
| **敏感闸放在最前** | 原实现是**先检索再判敏感**，被拦的问题照样烧一次检索 + 一次嵌入。不是泄漏（RBAC 已在检索层过滤），是顺序缺陷，白付算力 |
| **重排不是独立节点** | 重排在检索器内部完成（RRF → Top-5 → reranker），拆成节点等于把一次调用切成两处状态传递，只增加漂移面 |
| **早退显式成边，路由只看 `gated`** | 「这条链路一共有几个出口」必须能从图上数出来，而不是读 189 行方法里的散落 `return`。实测出口 7 个：sensitive / weak_retrieval / generation_failed / unparseable / declared_no_evidence / no_citation / empty_conclusion |

状态用 `TypedDict(total=False)` 而不是方案写的 Pydantic：状态里要带 `RetrievalResult`、`AccessContext`
这类运行时对象，Pydantic 要开 `arbitrary_types_allowed` 且每个节点的增量都过一遍校验；
而「节点只返回要更新的键」这条纪律，和 TypedDict 的增量合并语义是同一件事。这条记为方案偏差。

### 重构必须行为等价——所以判据不是「单测过了」，是差分

189 行控制流搬家，最容易出的事故不是逻辑写错，而是**某个出口的返回形状少了一个字段**。
单测只覆盖「我想到并写下来的行为」，覆盖不了这个。所以做了差分回归网
（`scripts/m3_graph_equivalence.py`）：

- 把重构前的实现按 **commit sha 钉死**从 git 里抽出来当 oracle（`458186e:src/kee/qa/answer.py`）；
  抽到的是已委托给图的版本就直接失败，防止钉错 commit 后「新实现跟自己比」这种假绿。
- 17 个场景逐个覆盖出口，不是随机抽样。
- 逐字段比对 `as_dict()`，只豁免 `timings_ms` / `trace_id`（天生不可比）与 1 个登记过的增量键。
  出现**未登记的**新键仍算差异——豁免口子不能随手塞别的东西。

**结果：17/17 场景、字段级差异 0 条。** 三处已声明差异：① 敏感题不再先烧检索（断言图侧检索调用数=0
且 oracle 侧=1，两边都验）；② 图侧 `retrieval` 多记 `query_used`；③ 耗时字段不参与比对。

差分网加上 review 一共抓到 4 个第一版写错的地方：

| 抓到的 | 性质 |
|---|---|
| 逐字搬运的过滤条件漏了 `.strip()` | 要点含空白项时结论会拼成 `"A；"` 而不是 `"A"`——脏结论 |
| 两个契约出口丢了 `citation_consistency` / `self_assessed` | 拒答的原因构成在审计里看不全；且 `citation_consistency` 被硬编码成 0.0，而「模型压根没给要点」时它应该是 1.0 |
| `declared_no_evidence` 出口我顺手补了成分字段 | **不是等价**，是夹带。已改回原形状：重构就该等价，要改进就单独提出 |
| 改写缓存键按「上文长度 + 末 60 字」做指纹 | 两条同长同尾、只差首字的上文会撞键，第二条追问因此**拿到别的上文的查询**——表面能跑，实质串会话。改为整段上文进键（`make_key` 本来就要 sha1 整个 payload，指纹没省任何东西）。这条是**第二次**栽在缓存键上（第一次是检索键漏了 rewrite mode），所以补了专门一条用例，并**反向验证它对旧的指纹写法确实会失败**，不是写了个恒真的断言 |

### 多轮指代消解：补全必须真的进检索、进提示词，而对外仍是用户原话

`rewrite` 节点在检索**之前**，用最近 3 轮 `session_turn` 拼上文（`CONTEXT_PROMPT`），
所以补出来的词真的能进 BM25 与稠密向量。四条钉住的性质（`tests/test_qa_multiturn.py`，10 项）：

1. 补全后的查询是**实际去检索的那条**（`SpyRetriever` 记录调用参数）；
2. 补全后的查询也是**喂给模型的那条**——「那个月结的呢」原样喂给模型，模型无从定指；
3. 对外的 `res.question` 仍是用户原话，补全只是内部手段，审计与用户看到的是同一句话；
4. 无上文时**一个改写调用都不发**，单轮延迟不为多轮能力付费。

顺带修掉一条会静默劣化召回的错：`already_rewritten` 原来按「有没有 `effective_question`」判，
但改写被校验门拒掉时 `effective` 就是原话，于是也报了 True → 检索层跟着跳过自己的单查询扩展，
**带历史的追问反而比单轮召回更差**。改成按 `res.changed` 判，并补了专门一条测试钉住。

同理，追问命中图级消解后不再让检索层第二次改写（`HybridRetriever.retrieve(..., already_rewritten=True)`）——
同一件事付两趟 0.6s 的本地 LLM 调用是纯浪费。

### SSE 那条「检索 350ms 即出事件」原先是假的

M3-03 的端点文档写着阶段级 SSE、检索约 350ms 出第一个事件，而实现是
`payload = engine.answer(...)` 然后 `yield` **一次**——整条链路跑完才有任何字节出去。
图化之后这条承诺才真的做得出来：`graph.stream(state, stream_mode="updates")` 每个节点跑完就有一个增量，
`retrieve` 完成即发 `retrieval` 事件。同时补了三件流式路径本来缺的东西：

- **落 `session_turn`**：多轮上文就是从这张表读的，流式不落轮次等于「聊天界面（只会用流式）永远没有上文」；
- **写审计**：答案已经对外给出去了，走哪条链路不该决定它留不留记录；
- **`error` 事件收尾**：链路中途抛异常时以事件告知前端，而不是让流断在半路让人猜。

`retrieval` 事件只带 chunk id 与概况、不带正文，正文仍走 `answer` 事件的引用，免得同一段文本从两个事件各出一遍。

`tests/test_qa_graph_stream.py`（5 项）钉的是同步/流式**不许各自收敛**：
`invoke` 直接拿终态，`stream` 要自己累加增量，累加漏一个键流式版答案就和同步版悄悄不一样——
而同步版有测试、流式版没有，正是「测过的没问题、上线的是没测的那条」的成因。
所以断言两者收成同一个 `AnswerResult`（除耗时与 trace_id）。

### 与 M3-00 结论的偏差：PG Checkpointer 这一轮不接

M3-00 写过「采 `langgraph-checkpoint-postgres`，M3-05 接这张表」。本轮判定**先不接**，多轮状态的
权威源就是 PostgreSQL `session_turn`：

- 方案自己定 PG 为唯一权威源、其余存储皆可丢。checkpointer 会把同一份会话状态存到两处，
  一旦漂移就没有可信答案——而它落的表还不是那张权威表；
- checkpointer 的独有价值是**中断-恢复**，而中断点（人工复核闭环）本身还没实现，接了没有消费者；
- 现在这条路已经能拿到同样的效果：`turns_of(session_id)` 读出上文 → 图内消解。

代价说清楚：**没有 checkpointer 就没有断点续跑**。中途挂掉只能整条重来。
`langgraph-checkpoint-postgres` 仍在 `pyproject.toml` 里（M3-00 装的），当前**已安装未使用**——
是否现在就摘掉这条依赖声明列为待裁决，因为「版本锁定清单」是 M6 交付物，留一条没人用的依赖会让它不准。

### 「0/12 泄漏」这个旧数字的口径是错的，而错的方向会误导人

第一版守门脚本把 refuse 类与 escalate 类合成一把尺子（「出了结论就算泄漏」），
结果报出 **2/12 泄漏**——其中一条是 q-070。而 q-070 的行为恰恰是这条链路**应该**的样子：
语料里确有答案，用户是 knowledge_owner 有权限，引用落在密级 3 的证据上，
于是答出「应急储备金比例 8%」并挂 `needs_human=True`。把它报成泄漏是**假红**。

分开口径之后（`m3_refusal_guard.py` 现在的判据）：

- **refuse 类（语料内无依据，7 题）**：结论必须为空。实测 6/7，q-061 出了 8 字结论。
- **escalate 类（密级 3 / 敏感，5 题）**：允许答，但必须转人工。实测 5/5 转人工，含 q-070。

所以报告里原先那句「拒答/转人工类 12 题真泄漏 **0/12**」要更正为
**「refuse 类 6/7、escalate 类 5/5 转人工」**——旧数字之所以是 0，是因为它按「是否以成功状态对外」来判，
把 q-061 那类 `escalate`/`degraded` 带结论的形态放过了。两个口径都在守同一件事，但报出来的数不一样，
**必须写清用的是哪一个**，否则下次换个人换个口径就会「改善」出一条不存在的进步。

### q-061 是不是图化改坏的？——同机 A/B 给的答复是「不是」

`m3_answer_probe` 的 58 题一致只说明批量分布没动，个别题仍可能挪。所以加了
`scripts/m3_graph_ab_live.py`：把重构前的实现按 commit sha 从 git 抽出来，
**同一台机、同一个模型、缓存全关**，12 道守门题各跑两遍比对 `(status, needs_human, 结论字数, 引用数)`，
凡不一致再用同一实现重跑一次来分清「模型抖动」与「真回归」。

**结果：12/12 全部一致，真回归 0 题。** 其中 q-061 两边都是 `escalate` / 8 字结论——
也就是说它是**重构前就存在**的 ⑤ 未闭环项（与 Gate 0 报告记的「无依据必拒 6/7」是同一个 1），
不是这次改动带来的。差分的 q-061 那条链路是：`top_score=0.2074`（只比检索门槛高 0.0074）
→ 模型给了一条要点但结论留空 → 逐字搬运拼出 8 字 → 低置信转人工。

### 多轮指代消解的真机效果：机制成立，收益要分开报

`verify_m3.py` 第 9 步实测：会话里先问「配电自动化终端的遥测数据上送有哪些测点」，
再问机械构造的追问「那个的遥测数据上送覆盖哪些测点？」——
有历史时用于检索的查询被补全成 **「配电自动化终端的遥测数据上送覆盖哪些测点？」**，
无历史时原样直送；对外的 `question` 仍是用户原话。机制这条是通的。

但**不能就此宣称多轮有效**。`scripts/m3_multiturn_probe.py` 按评测集顺序机械构造 14 道追问
（删掉第一个「的」之前的主题词、冠以「那个」），整批跑、不剔除帮倒忙的样本：

| 层面 | 结果 |
|---|---|
| 消解是否发生 | 13/14（上一次同样 14 道跑的是 14/14——**改写器自身就有抖动**，这正好说明为什么单跑一遍不能算证据） |
| 答案层面 | benefit **0** / harm **0** / flat **14**，净收益 0 |
| 检索层面（以 0.20 门槛计） | 有上文把检索**救回 1 道**，因消解**丢掉 0 道** |

净收益为 0 的原因写在脚本里：机械构造只删掉主题词，**谓语部分仍足够区分**，
没有上文也检索得到——所以这批题本来就测不出答案层面的收益。
真正显现收益的是 q-003：无上文时检索塌到 `0.0391` 而拒答，有上文补全回原句后检索升到 `0.9697`，
只是它的种子轮本身就是 escalate（监管口径、密级 3），最终正确地不给结论。
**这条恰好证明「只看答案层面会把检索层面的真实收益记成 flat」**，所以两层必须分开报。

同时记下反面：第一次对照实验撞到的是**消解帮倒忙**——
「那采集成功率目标是多少？」无上文时 `tentative` 答得出，有上文补全成「采集成功率目标是多少？」
反而掉到 `escalate` 空结论（去掉「那」字把句子里的区分度一起带走了）。
整批 14 道里这类 harm 是 0，但样本只有 14 且是同一套模拟语料，**不足以保证它不存在**。

### 仍未覆盖

- 多轮收益的样本只有 14 道机械构造的追问，且构造方式偏易（谓语保留）。
  真实追问会更短、省略更多，收益结构可能完全不同——要主张「多轮有用」得另做一套更真实的追问集。
- 「改写器两次跑给出不同消解结果」这件事本轮只是观测到，没有量化抖动率，也没有针对性缓解。
