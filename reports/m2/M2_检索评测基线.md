# M2 检索评测基线（真机实测）

> 生成时间：2026-10-10 · 执行：`scripts/m2_eval.py`（可复跑）· 原始证据：`var/gate0/m2_eval.json`
> 环境：RTX 4060 Laptop 8188 MiB；Milvus v3.0.0（集合 `kb_chunks`，193 子块）；PostgreSQL 18 权威源；
> BGE-M3 + BGE-reranker-v2-m3 fp16/CUDA 常驻；Ollama qwen2.5:7b 同时常驻（实测结束显存 7992.6/8188 MiB）。

> **口径声明**：语料为**模拟行业语料**（24 篇我方生成的事实卡），gold 是构造时按关键词回查出来的，
> 因此本文数字代表「达成路径是否存在」，**不是上线承诺值**。所有指标附样本量 n；
> 未达到的门禁如实写「不通过」，不折算成通过。

## 一、结论

| 判定 | 结论 |
|---|---|
| 检索链路能力 | **达标**。strict gold 口径 Recall@5=**0.965**、Hit@5=**0.9828**、MRR=**0.9698**（n=58） |
| 检索延迟 | **达标**。P50 315.7ms / P95 338.4ms / P99 355.5ms / max 373.7ms，门禁 800ms |
| 方案 DoD #2「Recall@5 ≥ 85%」 | **按 section 级 gold 判定为不通过（0.822）**；但缺口不是检索失败造成的，见第二节 |
| 参数是否是瓶颈 | **不是**。9 格 OFAT 网格的最大增益落在噪声地板以内，见第三、四节 |
| 查询改写 | 已接入并有正增益（dev strict +0.0417），但**P95 2.1s，超检索门禁 2.6 倍**，默认关闭 |
| 表格单元格级检索 | 从「整表一块时 Top1 命中 gold 率 0.0」做到行级 `列名=值` 的 **Hit@5 0.833**（n=12，独立集合）；剩余 2 题是**重排压制**了正确行，不是检索不到 |

95% 置信区间宽达 0.13（[0.7553, 0.8858]），任何小于 0.065 的参数改动都无法与噪声区分。

## 二、基线与两套 gold 口径（这是 0.822 的真正来源）

评测集 gold 有两种定义，M2 之前只报前者：

| 口径 | 定义 | Recall@5 | Hit@5 | MRR |
|---|---|---|---|---|
| **section 级**（Gate 0 ③ 沿用） | 关键词命中在章节父块 → 该章节**所有**子块都算 gold | **0.822** | 0.9828 | 0.9828 |
| **strict 级**（正文真含关键词的子块） | 只有本身包含全部关键词的子块算 gold | **0.965** | 0.9828 | 0.9698 |

逐题拆解证明 0.822 与 0.965 之间的差距**全部来自 gold 定义，不是排序失败**：

| 分层 | n | Recall@5 | Hit@5 |
|---|---|---|---|
| gold ≤ 5 的题 | 52 | 0.8497 | — |
| gold > 5 的题（最多 13 个 gold） | 6 | 0.582 | **1.0** |
| 全体 | 58 | 0.822 | 0.9828 |

- 6 道 gold>5 的题里，**每一道 Top-5 都命中了 gold**（Hit@5=1.0），只是 Top-5 装不下 11~13 个同级章节子块。
  一道 gold=13 的题，Recall@5 的理论上限就是 5/13=0.385。
- 全体 Recall@5 的理论上限（排序完美）= **0.9608**，门禁 0.85 并非不可达，但代价是必须取全章节。
- 抽查看到的具体形态：`q-003`「监管口径对拨备覆盖率的最低要求」与 `q-013`「SIS 表决逻辑与整定值」
  都在 **TOP1 以 0.97 / 0.95 的重排分命中 gold**，却因同级另一子块未进 Top-5 被记 recall=0.5。
- 真正的零召回只有 **1 题**（`q-044`，口语化「想直接进库里把字段改回来」，gold=2），
  且其 Top-5 重排分全部 ≤0.005 —— 检索层对这道题的正确行为本来就是「没有可用证据」，
  会被答案层 `min_retrieval_score=0.20` 拦成拒答/转人工。

**因此**：DoD #2 只写了「Recall@5 ≥ 85%」，没写按哪套 gold 判定。按 strict 已过（0.965），
按 section 未过（0.822）。这是**需求歧义**，不是实现缺陷 —— 见第八节待裁决，我不自行改判。

## 三、dev/test 拆分与噪声地板

参数网格如果在同一份数据上跑完再挑最好的一格当结论，就是「在测试集上调参再报测试集分数」，数字会系统性虚高。
所以本作业固定：

- 按 `qid` 的 CRC32 取模分半（mod 10，<4 为 dev）→ **dev 31 题 / test 39 题**（可判题 dev 24 / test 34），拆分规则写死在脚本里、可复跑核对。
- **基线配置是预先声明的**（`mode=hybrid, rerank=on, candidates=20, rewrite=off`，与 settings 一致），没有在这份数据上调过，
  所以门禁判定用**全样本 full**（n=58）而不是任一半。
- 网格**只跑 dev**，用于诊断方向；网格里最好的格子**不构成放行依据**，要转正必须先改基线声明再重跑。

噪声地板：dev n=24，一道题对 Recall@5 的影响约 0.021（section）/ 0.042（strict）。
第四节所有格子之间的差距都在这个量级上，**读数只能读方向，不能读大小**。

顺带暴露的分半偏置：dev Recall@5=0.7744、test=0.8556 —— 差 0.081，纯粹是小样本随机划分的结果。
如果当初拿 test 半区去判定门禁，就会得到「0.85 通过」的**假绿**。这就是本节存在的理由。

## 四、参数网格（OFAT，dev n=24）

基线在 dev：section 0.7744 / strict 0.9356 / P95 338ms。

| 格子 | 改动 | section Recall@5 | strict Recall@5 | P95 ms | 判读 |
|---|---|---|---|---|---|
| dense_only | 只稠密 | 0.7706 | 0.9252 | 335.8 | 与基线差 0.004，**BM25 腿在 Top-5 上贡献≈0** |
| sparse_only | 只 BM25 | 0.7004 | 0.8939 | 5.8 | 明显最差，但不花钱（5.8ms） |
| hybrid_no_rerank | 去重排 | 0.7568 | 0.9252 | 49.6 | 重排值约 +0.017 section / +0.010 strict，省 289ms |
| rrf_k_20 / rrf_k_120 | RRF k | 0.7744 | 0.9356 | 334~337 | **完全无差别**：两路 top-20 高度重合，k 不敏感 |
| candidates_50 | 重排候选 20→50 | 0.7883 | 0.9356 | 562.7 | section +0.014 但 strict **零增益**，多花 224ms → 不采纳 |
| topk_wide_40 | 两路 top_k 20→40 | 0.7744 | 0.9356 | 352.5 | 无变化 |
| rewrite_sparse | 改写喂 BM25 | 0.7953 | **0.9773** | **2099.7** | 唯一有方向的增益，代价是 P95 超门禁 2.6 倍 |
| rewrite_extra_leg | 原+改写各算一路 | 0.7953 | 0.9773 | 2076.4 | 与 sparse 同分，多一次检索无额外收益 |

结论：**没有任何参数组合能在 800ms 内把 section Recall@5 推过 0.85**，而且这些差异本身都在噪声地板内。
真正的杠杆是（a）gold 口径的定义、（b）评测集规模，不是调参。

## 五、查询改写实测（`scripts/m2_rewrite_probe.py`）

链路已接入（`kee/retrieval/rewrite.py` + pipeline 的 `rewrite_mode`），默认 `off`。

**触发率**：70 题里启发式判定需要改写 **19 题 = 27.1%**（指代/省略/短查询），其余透传不花 LLM 调用。

**全量 70 题实测（模型常驻、去掉冷启）**：

| 指标 | 值 |
|---|---|
| 单次改写 P50 / P95 / max | **625.4 / 842.7 / 986.1 ms** |
| 改写生效数 | 65 / 70 |
| 校验拒绝数 | 3（全部为误拒，已修，见下） |
| JSON 解析失败数 | **0**（修复前 21） |
| 超预算数（budget 900ms） | 2 |

**验证过程修掉的两个真缺陷**：
1. **`num_predict=64` 把 JSON 截断**：原提示要求模型同时输出 `reason`，理由字段吃到 token 上限后整段 JSON
   不闭合，`json.loads` 失败 → **70 题里 21 题的正确改写被直接扔掉**（30% 自伤）。修法：输出只留
   `expanded`、上限提到 96、并对「值已闭合、括号缺失」的截断做正则打捞（要求引号成对，
   截断在未闭合字符串里的不会被误捞）。修后 P50 从 1338ms 降到 625ms、失败数 21→0。
2. **收尾句号误拒**：3 条被判废的改写全是「用户原句本身以「。」结尾、模型照抄」。改为规范化掉
   尾部句读再校验，只拒「句内多句结构」。

**安全约束（不是可选的）**：改写**禁止引入原查询没有的数字**（校验会拒），因为检索错只是找不到，
改写凭空造出项目编号会让下游引用指向不存在的内容 —— 那是引用造假。重排一律用**原查询**打分：
改写为召回服务，判「这段是否回答了用户问的话」不能拿改写后的字面去判。

**延迟裁决**：改写一次 P95 843ms，而检索门禁是 800ms —— **单这一步就吃满整条检索预算**。
所以 `rewrite_mode` 默认 `off`；要常开必须先在「改写不计入检索 P95」还是「门禁上调」上做出裁决
（第八节）。当前证据支持的是：改写对 strict 口径有 +0.042 的方向性增益，代价未偿清。

## 六、M2-01 基线索引重建（统一 chunk-id 命名）

Gate 0 遗留的 193 块（含父块共 333）仍是修复前的**双前缀**命名 `doc@doc@v1#1.1#c1`，
而 M1 新摄取用 `doc@v1#…`。用修好的 `chunk_document` 全量重建，`scripts/m2_rebuild_baseline.py`
带四项自证校验，全部通过：

| 校验 | 结果 |
|---|---|
| 正文逐块不变（按 版本+章节号+块序 对齐） | 333 块键集合相同、**内容漂移 0 块**、页码漂移 0 |
| chunk-id 命名统一 | 旧双前缀 333 → **0**；不匹配新式命名 0 |
| gold 映射等价 | 70 题、**gold 漂移 0 题**（改名前后逐题一一对应） |
| 索引与权威源一致 | 权威源子块 193 = 分块表 193 = Milvus 193 |

重建前已把 `vectors/`、`eval_set.json`、`qrels.jsonl` 备份到 `var/gate0/pre_m2_rebuild/`。
**重建没有改变任何检索指标**（0.822 与 Gate 0 ③ 完全一致）—— 这本身就是重建正确性的强证据：
语料是 `FACT_CARDS` 直接生成的卡片、不经解析器，正文只允许 id 变。

一个顺带量到的运营事实：全量重建 274.5s 里**嵌入只占 1.91s**，其余约 268s 是权威源写入 +
Outbox 派发 + Milvus 插入/flush。也就是说「索引可重建」这条原则的时间成本在**存储侧而不是 GPU 侧**，
M4 的一键 Demo 与运维口径要按这个数排。

## 七、表格检索专项（`scripts/m2_table_probe.py`）

主评测集是生成的事实卡、**不含任何 Markdown 表格**（实测 24 篇 0 段），所以「表格结构已接」这句话
在 M1 只验证到「块存在且被切分」。本节补的是真正的缺口：**用户问某个单元格时，能不能检索到那一行**。

跑在独立集合 `kb_m2_tables` 上，5 份表格文档（1 真实扫描件 + 4 合成）、12 道单元格级问题，
gold 用**结构式定义**（该文档内含答案行的表格行块，空格不敏感匹配），跑完清库、主基线 193 块不受影响。

### 三轮迭代：每一轮都是上一轮的失败教我的

| 表示法 | Recall@5 | Hit@5 | MRR | Top1 即 gold 率 |
|---|---|---|---|---|
| ① 整张表一个子块 | 0.500 | 0.667 | 0.207 | **0.0** |
| ② 行级 + 重复 Markdown 表头 | 0.636 | 0.750 | 0.241 | 0.091 |
| ③ 行级 + `列名=值` 渲染 | **0.833** | **0.833** | **0.479** | 0.25 |

三个机制依次被暴露：

1. **整表一块打不过短句**。BM25 按长度归一化，200 字的表块被 20 字的旁注块（"注：以上数据取自出厂检验记录"）压过；
   嵌入又把 8 行平均成一个向量，对单行提问没有区分度。→ 12 题 **Top1 命中 gold 率为 0.0**。
2. **「表头 + 一行」的残块行行不可分**。每块都带同一段表头和同一个章节前缀，共享文本占块内 60%+，
   实测 Top-5 在同一张表的各行之间近似随机排列（"试运行阶段要交付什么" 召回的是质保/验收行）。
3. **`列名=值` 把区分度还给行本身**，Hit@5 从 0.667 抬到 0.833，真实扫描件 hak180 的 4 道题全部命中。

### 还没解决的那 2 题：是重排把正确答案埋了

定位实验（同一份数据、同一道题，只切重排开关）：

| 查询 | 无重排命中名次 | 有重排命中名次 |
|---|---|---|
| 试运行阶段要交付什么 | **1** | 2 |
| 结项阶段的交付物 | **1** | 4（在 5 文档集合里掉出 Top-5） |

也就是说**检索层已经把它排在第一位，是 BGE-reranker 把正确的表行块压了下去**。
机制推断：交叉编码器在 `A: 问题? B: 段落` 形态上训练，判的是「这段是否自然回答了问题」，
而 `阶段=试运行；交付物=试运行报告` 是键值碎片、不是句子，得分天然低于同集合里的自然语言块。
这是表示法之间的真实张力：**帮 BM25/嵌入的写法害了重排**。

两条候选修法（都要成规模的数据才能定，当前 n=12 不足以选）：
(a) 表行块**不进重排**，按融合名次保留，只重排正文候选；
(b) 行块渲染成**自然语言短句**（"表3里程碑与交付物对照：阶段为试运行，交付物为试运行报告"），
    既短又术语密集，同时是交叉编码器能判的形态。

### 顺带修掉的一个探针自身缺陷

`框架 L 单元` 一度被判成「找不到 gold」，实际是 OCR 对同一列名在不同行给出不一致的空白
（`型号=框架L单元` 与 `型号=框架 R 单元` 并存）。gold 匹配改成空格不敏感。
——这个错如果留在探针里，会被当成一次检索失败记进结论。

## 八、已知限制（不得当作已完成）

1. **评测集规模不足**：n=58 可判题，Recall@5 的 95% CI 宽 0.13。当前样本量无法支撑「参数 A 优于 B」的结论，
   只能支撑方向性判断。扩样本（更多题 + 更多文档）比调参更有价值。
2. **gold 是构造时关键词回查出来的，不是人工判相关性的**。第二人标注复核表仍是占位
   （`var/gate0/annotations_a2_template.csv` 有 71 处 `TODO_ANNOTATOR2`），**Cohen's Kappa 未出**。
   「相关」的口径目前只有单人定义。
3. **表格行块会被重排压制**：检索层已把正确行排到第 1 位，加上 BGE-reranker 后退到第 2/4 位
   （见第七节定位实验）。当前 `列名=值` 表示法对 BM25/嵌入友好、对交叉编码器不友好，
   12 题里仍有 2 题因此落出 Top-5。**修法未定**，不能继续在 n=12 上试出来。
3b. **多行表头的表会丢列名**：hak180 表头是「型号 / 有害物质(跨 6 列)」两行结构，Markdown 只能表达一行，
   于是 铅/汞/镉… 这些真列名落到数据行里，行块渲染成 `有害物质=X；列3=O；…`——按列名提问检索不到这些列。
4. **多轮追问的指代消解未测**：改写的启发式触发会认出「它/这个/上面」，但评测集里没有真多轮题，
   指代补全的正确率未测。
5. **分半偏置**：dev 0.7744 vs test 0.8556，说明当前规模下任意划分的分数都不稳；本节已把判定改成 full，
   但这也意味着 dev/test 拆分对「防止调参过拟合」的保护力有限。
6. **未做**：查询改写的多查询变体（同义改写取并集）、rerank 分数阈值自适应、跨文档 gold 的分层打分。
