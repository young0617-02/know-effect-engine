# M5 · 检索缺口归因（#58：唯一那道漏召题，以及为它标价的四把钥匙）

> **口径声明**：本文数字为真机实测（RTX 4060 8GiB / 本地 BGE-M3 + BGE-reranker-v2-m3 / Milvus 193 块 /
> 80 题评测集，其中可答题 68）。语料含模拟件，绝对值只代表「达成路径是否存在」，不构成上线承诺。
> 跑法：`uv run python scripts/m2_retrieval_gap.py`（全量归因）与
> `uv run python scripts/m2_retrieval_gap.py --explain q-044,q-046,q-047,q-051`（机制探针）。
> 证据：`var/gate0/m2_retrieval_gap.json`、`var/gate0/m2_retrieval_gap_explain.json`。

## 一、结论先说

**当前生产配置下，68 道可答题里只有 1 道漏召：q-044。** 不是「口语化一片皆输」——
口语化 14 道里 13 道命中，Hit@5(strict) 整体 0.9853。所以这一节的产出不是「修好了一个指标」，
而是**把这条缺口的机制钉死，并给所有可能的修法标上实测代价**，其中代价最小的那条**并不便宜**。

四件事，按可信度排：

1. **机制 = 稠密腿完全不认这句口语，BM25 认，但被 RRF 埋了。**
   q-044 三块 gold 在**原查询**下的名次：稠密腿 **前 50 全无**（None），BM25 排 **7 / 17 / 28**，
   融合后落 **26 / 37 / 52**——生产重排池只取融合前 20，于是重排**从没看过它们**。
   同一道题把书面语的词喂进去（上限检验，见第四节为什么不能用它当功能）：稠密 #3/#9、BM25 #1/#2、**融合 #1/#2**。
   ⇒ 瓶颈是**词法**（口语「进库/改回来/堵死」对上书面「不得直连修改/追加更正/审计追踪」），不是排序算法。
2. **免费的三把钥匙全部无效**：`rrf_k 60→20`、`rrf_k 60→10`、`dense/sparse_top_k 20→40`——
   后一条几乎不加时间（p95 322.5ms）却**一道题都没翻过来**。
3. **唯一有效的配置是「腿 40 + 重排上限 50」，代价是把检索门禁吃干**：
   @5 67→68、strict 67→68，但 **p95 319.3 → 759.8ms**，而门禁是 **P95 < 800ms**——
   余量从 478ms 缩到 **40ms**。#56 量到的这台机器的延迟噪声地板是 **93.6ms**，
   40ms 余量意味着**下次复跑大概率顶破门禁**。
4. **所以我的建议是：不要为一道题买这个配置。** 这一格保持现状 + 把缺口登记在案；
   真要收这条口子，正确的战场在**索引侧**（见第五节），不在参数侧。

⚠ 三点读法纪律：
- 这六行都是 **what-if**，没有一行是已经改了的口径；真要落地得按「原口径 / 修订口径 / 实测依据」三件套
  改 `config.py` 并重跑 `m2_eval`（一支改动一次重跑，改前留档）。
- 「@5 命中」在这里是**题级** hit（前 5 里有 gold），不是门禁那条 Recall@5——两者口径不同，别混着引。

  这道题在旧尺子上本来就悬在噪声里（V1.18 量到旧题面下第 1 名只领先第 2 名 **0.0002**）。

## 三、词法假说：类别层面成立，但它不是「一片皆输」

| 类别 | n | Hit@5 | 题面与 gold 的词重合度均值 | 与当届第 1 名的重合度均值 |
|:---|:---|:---|:---|:---|
| **口语化** | 14 | 0.929 | **0.239** | 0.192 |
| 术语 | 16 | 1.000 | 0.749 | 0.719 |
| 编号 | 13 | 1.000 | 0.746 | 0.725 |
| 方案名 | 12 | 1.000 | 0.763 | 0.757 |
| 跨文档 | 13 | 1.000 | 0.654 | 0.629 |

重合度 = |题面词 ∩ 块词| / min(两者)，jieba 分词，块正文的分块标题前缀已剔除。全库重合度 < 0.3 的题**一共 11 道，全部是口语化**。

假说的**方向**被证实（口语化题面的词就是落在证据里的少，3 倍差距），但两个必须同时说的限定：
- **低重合 ≠ 漏召**：口语化 14 道里 13 道照样命中——稠密腿把词法缺口补上了（例如 q-051：BM25 前 50 没有，靠稠密 #1 进池）。
- 在**唯一那道漏召**上，gold 的重合度（0.1765）反而**高于**当届第 1 名（0.0）。
  所以「gold 被一个词面更像的干扰块挤掉」这个我原本预设的故事**不成立**；
  真实形状是：**词没对上 → 稠密腿彻底不认 → 只剩 BM25 一票 → RRF 把它埋到 26 名以后**。

## 四、机制探针与它的边界（为什么那行「+gold_keywords」不能当功能）

`--explain` 对四道题各跑三种查询，报 gold 在**每条腿**与融合列表里的名次（节选）：

| 题 | 查询 | gold 的稠密名次 | BM25 名次 | 融合名次 |
|:---|:---|:---|:---|:---|
| q-044（漏召） | 原查询 | **None / None / None** | 7 / 17 / 28 | 26 / 37 / 52 |
| q-044 | 原查询 + gold_keywords | 9 / 3 / None | 2 / 1 / 19 | **2 / 1 / 38** |
| q-044 | 只查关键词 | 3 / 1 / 40 | 2 / 1 / 37 | 2 / 1 / 15 |
| q-051（命中） | 原查询 | 1 / 39 | None / None | 12 / 69 |
| q-047（命中） | 原查询 | None / 27 | 2 / 35 | 24 / 16 |

**「原查询 + gold_keywords」这一行是偷看答案的上限检验，不是可上线的改写策略**——
`gold_keywords` 本身就是从 gold 正文里取出来的词。它唯一的用途是回答一个二元问题：
**「词都对上了还检不到吗？」** 答「不，词对上就是第 1 名」⇒ 瓶颈确定在词法侧，
于是就不该再去调排序参数（第四节前三把钥匙的无效也印证了这一点）。

顺带一条与本节同级的事实：q-044 在生产配置下**前 5 名的重排分只有 0.007**，rank1 领先 rank2 **0.0035**——
那是「池子里根本没有像样的候选」的形状，不是「两个好块争第一」。

## 五、真要收这条口子，正确的战场在哪

参数侧已经量到头了。剩下的路按代价排：

1. **索引侧补一层「书面语别名」**（推荐方向，未实施）：入库时给每块生成一份术语化摘要/别名域，
   BM25 与稠密都多一条可命的腿。它是**离线一次性成本**，不加在线延迟——
   这正是它比「查询侧改写」便宜的理由：查询侧每问都要付一次模型时间。
2. **查询侧 LLM 改写**：已实测过成本，**单步 P95 843ms 就吃满 800ms 检索门禁**（M2 的裁决，默认 `off`）。
   买它等于再叠一层「为了 1/68 道题把门禁顶破」，比第四节那条更贵。
3. **接受并登记**：当前默认走这条。理由不是「已经够好」，而是
   **DoD 的检索门禁本来就是 Hit@5 ≥ 95% + strict Recall@5 ≥ 85%**，
   现值 0.9853 / 0.9779 都过；而为最后一道题把 p95 余量压到噪声地板以下，
   会让**门禁本身**变得不稳定——那是为了指标表面好看去牺牲可复核性。

⚠ 这一节**没有实现 1**，因为改索引 schema 会动 gold 映射与全库重跑（与「一支改动一次重跑」的纪律冲突），
且它需要用户裁决范围。今日产出是**归因 + 标价 + 把三条路的代价摊开**，不是悄悄挑一条走了。

## 六、这一节暴露的两处我自己的错（照例留在报告里）

1. **第一版把 q-044 判成 `cut_by_pool`（扩重排池就能救）**——因为宽配置同时动了腿宽与候选上限两个旋钮，
   我拿它当单因子证据用了。实测 `rerank_candidates 20→40` **单独跑完全不翻转**，才看清真因在融合名次。
   ⇒ 已在脚本里把成员关系**逐个配置**记下来（`pool_membership`），诊断只由布尔按固定 precedence 推出，
   并加了 `needs_rc / needs_legs / needs_both / needs_deep` 四种分开写，不再混成一个标签。
2. **原以为是「干扰块词面更像挤掉了 gold」**——实测相反：漏召那道题上 gold 的重合度高于第 1 名。
   ⇒ 假说的**方向**（词法不重合）被数据支持，假说的**机制故事**被数据否掉；
   报告里两件事分开写，不因为方向对了就放过故事错了。
